# Brief - tb-storage-root-identity

## Goal

Close GitHub issue #159. The installer root and the scratch root keep opening
after the host renumbers the volume's device (`st_dev`), which macOS APFS can do
across a reboot or an OS update. They still refuse a replaced, foreign or
substituted directory. The CLI test suite never reads host installer storage.

Observable outcomes:

- A root whose `owner.json` names the same inode, owner, kind and private mode
  but an older `dev` opens when that record file was last written before the
  current boot (its modification time precedes the boot's start, from
  `os.uptime()`). This holds for a root at a volume's mount point too. A writing operation re-records the current `dev`; a read-only
  operation (preview, Doctor) accepts the old value without writing. No record
  field is added: existing records on affected hosts are covered as they are.
- A root is still refused with the existing ownership error when its `dev`
  differs from a record written in the current boot, when its inode differs (a
  copied, restored or recreated directory, or another volume mounted at the root
  path, whose top directory has the volume-root inode), or when its owner, kind
  or private mode is wrong.
- Records inside a verified root (installer entries and their retained file
  stamps, scratch runs) match by inode and must sit on the root's current
  device, so a renumbered device does not leave every entry `uncertain` and
  block cleanup. A root's `entries`, `runs` and `reports` directories must be on
  the root's device.
- `cli/test/scratch-cleanup.test.js`'s `cleanup` invocation sets
  `GATEREEVE_INSTALLER_ROOT` to a fixture directory.
- Regression tests, for both roots: a record from an earlier boot with a changed
  `dev` and the same inode opens and is re-recorded; the same record written in
  this boot is refused; a copied root is refused.

## Threat model

The ownership check guards cleanup from deleting what GateReeve does not own: a
foreign or other user's directory, a symlink or rename substitution, a directory
replaced or recreated since its record was written, and another filesystem
mounted at the path. Same-user processes can write any record and file time, so
they are not a boundary this check defends (as before this change). Within one
process, device and inode are still compared together, so mid-operation
substitution is caught as before.

One case cannot be told apart from the renumbering the issue requires us to
accept, by this rule or any rule based on records inside the filesystem: a
filesystem that, at the root's path, has a directory with the recorded inode
number and a copy of the root's records, written before this boot and not yet
re-recorded in it. An arbitrary foreign filesystem does not reproduce the inode
and records; producing them takes either a clone of the user's own volume (for
example a block-level restore, whose records describe GateReeve's own managed
data) or deliberate same-user preparation, which is outside the boundary above.
Accepting the renumbered genuine root is the issue's goal, and that root and
such a replica are identical to every check that reads the filesystem, so a
stricter rule would refuse the genuine root again. The previous check refused
the replica only because it also refused the genuine root after every
renumbering, which is the bug.

## Rigor

Light, by the human's explicit choice for this run, made while naming this as a
security-relevant ownership check and asking for the reasoning to be recorded in
the decision log. The change keeps every existing check and record format and
relaxes one comparison under a narrower condition. The deterministic tripwires
at `candidate.prepare` remain the escalation trigger; under goal autonomy a hit
raises the run to full rigor automatically.

## Scope

In:

- `plugin-src/shared/resources/storage/scratch.js` and `installers.js`, and their
  staged desktop copies under `apps/desktop/resources/storage/` (regenerated by
  `apps/desktop/scripts/stage-protocol.mjs`).
- `cli/test/scratch-cleanup.test.js` and `cli/test/installer-retention.test.js`.
- `plugin-src/shared/resources/STORAGE.md`: one paragraph on root identity.

Out:

- Any change to in-process identity checks (dev and inode compared within one
  process stay strict), lock semantics, deletion rules or record formats. The
  only record write added is re-recording a root's `dev`.
- Reviewer pipeline, `review.publish` and `briefScope` files (other threads).
- The host's own installer and scratch roots are not deleted or edited by hand.

## Findings log

- 2026-11-27: The issue names only the root records, but installer entry records
  (`same(record, stat)` in `load`), their retained file stamps (`equalFile` in
  `inventory`) and scratch run records (`loadRun`) also persist `dev` across
  processes. After a renumbering they would all fail, leaving every entry
  `uncertain` and blocking cleanup, so they are in scope (same rule, no
  re-record).
- 2026-11-27: Chosen identity rule: compare the recorded inode (plus the
  existing kind, uid and private-mode checks); keep `dev` as the last observed
  value. A random root ID stored inside the directory was rejected because it
  cannot detect a replaced directory. See scratchpad.md.
- 2026-11-27: Brief review round 1 (FAIL) found that inode-only matching would
  accept another filesystem carrying the same inode and records. The rule now
  binds a changed `dev` to an earlier boot: a same-boot device change is refused.
  Scratchpad entry [2] supersedes [1].
- 2026-11-27: Re-recording the installer root's `owner.json` must happen under
  the storage lock: that file also carries `successSequence`, and an unlocked
  rewrite could undo a concurrent increment.
- 2026-11-27: Added a same-device check between a root and its `entries`,
  `runs` and `reports` subdirectories, so tolerating a renumbered root does not
  admit a tree that spans filesystems.
- 2026-11-27: This host reproduces the issue: the installer root record holds an
  older `dev` with the same inode, and its entry and file records do too. The
  installed CLI from `main` reports `Installer root ownership changed`; this
  branch's `cleanup` preview opens the root, lists the keeper as
  `latest-successful` and leaves the host record unchanged (preview is
  read-only). `cleanup --apply` was not run on the host: it would delete real
  scratch runs.
- 2026-11-27: Brief review round 2 (FAIL) found that the boot-identity field was
  a record-format change and that records without it were treated as an earlier
  boot. The rule now compares the record file's modification time with the
  current boot's start, which needs no new field and treats existing records by
  when they were actually written. Scratchpad entry [3] supersedes [2]. The
  remaining indistinguishable cases are in the threat model.
- 2026-11-27: Host check: the installer root record was last written on
  2026-11-20 and the host booted on 2026-11-21, consistent with a renumbering at
  reboot; the branch opens it.
- 2026-11-27: Brief review round 3 (FAIL) found that a foreign filesystem
  mounted before the first writing operation of a boot could carry a copied
  record and the same inode. A parent-device condition was added (entry [4]) and
  then reverted after round 4 showed it refuses a legitimately renumbered root
  at a mount point while adding almost nothing: a volume mounted at the root
  path has the volume-root inode, which a non-mount-point root's record does not
  name. Entry [5].
- 2026-11-27: Brief review rounds 1-4 repeated two dissents that further
  revisions cannot resolve: the light-rigor choice for a security-relevant
  change, and the replica case in the threat model. They are settled by recorded
  autonomous judgment rather than by more review rounds.
