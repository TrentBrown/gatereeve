Review slices without creating intermediate pull requests

This change adds an opt-in synthetic review transport for slice boundaries while preserving ordinary pull requests as the default and requiring a real integration-to-release pull request for feature-final review.

Background

The constraint

Quality Process needs reviewable slices without filling GitHub's pull-request list. Other users should see no behavior change. The final promotion from an integration branch into the release branch must still use a real PR.

The switch

Each repository chooses sliceBoundaryMode. Omission means pull-request; synthetic-commit is explicit. releaseBranch defaults to the integration branch, preserving historical one-branch repositories.

Intuition

1. Pinintegration SHA + topic SHA
2. Buildone-parent exact-tree commit
3. Publishdeterministic review ref
4. Reviewcommit URL + captured comments
5. Promoteexact reviewed SHA

The synthetic commit is not an approximation of the reviewed content: its tree is the finalized slice tree, and its sole parent is the pinned integration SHA. After explicit acceptance, integration advances to that same commit with a normal non-force push.

Code map

Configuration and compatibility

The JavaScript and Python context resolvers agree on defaults, explicit modes, release roles, and Git-compatible branch validation. Historical PR contexts and PR_BOUNDARY model locks remain readable.

Transport-neutral boundary context

BoundaryContext gives gates common base/head/source fields and nests only the transport-specific review identity. Synthetic contexts carry the feature ID, candidate SHA, review ID, and deterministic review ref.

Safe publication

synthetic_review.py re-resolves the active workflow configuration at the mutation point. It derives the only permitted ref from feature ID, repository alias, and candidate SHA; a persisted alternate ref is rejected before commit creation or push. It also rejects dirty/detached state, moved bases, existing refs, and undeclared source changes.

Evidence and promotion

Commit comments are captured and fingerprinted. Promotion requires explicit human acceptance naming the reviewed SHA, then rechecks the configured ref, remote base, local source, tree, parent, and receipt before advancing integration.

Final PR boundary

Synthetic transport is rejected at feature-final scope. When integration and release branches differ, the final PR must be integration → release and retains both complete-feature and final-slice comparison ranges.

Why the failure cases matter

Invalid branch name: configuration now rejects the lone @ and DEL/control characters instead of accepting names Git cannot represent.

Wrong destination ref: even a syntactically valid alternate branch cannot be smuggled through a modified context. A bare-remote regression test proves neither the wrong ref nor the expected ref is created.

Provider mismatch: GitHub identity is validated before publication, avoiding a partially published review when URL construction cannot succeed.

Five-question review check

1. What happens when sliceBoundaryMode is omitted?
2. Which object is promoted after synthetic acceptance?
3. How is the review destination protected?
4. Can synthetic transport replace the final integration-to-release PR?
5. What does promotion recheck?
