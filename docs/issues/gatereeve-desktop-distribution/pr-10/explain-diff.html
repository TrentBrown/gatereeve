Background

GateReeve is one product with two independently installed surfaces. The Plugin governs work inside Codex or Claude; Desktop is the optional read-only window onto that work. The previous slices made Desktop self-contained, added Setup and compatibility, and produced one universal Mac DMG. But the old release path still understood only the Plugin.

The old risk

A Plugin tag and a Desktop DMG could be built at different times, from different commits, and then coordinated by convention. A failure halfway through publication had no durable answer to “what already happened?”

The new contract

Both candidates enter one record with one semantic version, one source commit, checksums, verification evidence, trust state, approval state, and per-surface receipts.

This PR still publishes nothing. It creates and tests the protocol for preparation and recovery. Apple trust comes next, and the first public RC still requires the user's approval of the exact record.

The compact release model

The record is deliberately narrower than a general workflow engine. It answers six release questions: which version, which source, which Plugin tree, which DMG bytes, which evidence and trust, and how far publication has progressed.

RC versions such as 0.1.0-rc.4 remain the GateReeve product version in the staged package and compatibility metadata. macOS receives the numeric base 0.1.0 where its bundle field requires it. Verification checks both representations rather than treating the difference as an accident.

Recovery is convergence, not rollback

2. PluginMarketplace tree

No transaction can atomically change Git, a marketplace branch, GitHub Releases, an update manifest, and a website. The model therefore records a completed prefix. Each adapter means “make this exact identity exist and tell me its durable identity,” not “blindly create another one.”

remote mutation succeeds
local record write is interrupted
retry asks the same adapter to converge the same identity
adapter discovers the existing result
record persists its receipt and continues

The fault test performs that interruption at every one of the five boundaries. In every case the final record reaches published and each simulated remote receives one mutation—not two.

Code walkthrough

Preparation

The manual GitHub workflow resolves a commit before candidate work. Independent jobs build the Plugin marketplace and universal DMG. Native ARM and Intel jobs inspect the same downloaded DMG and emit evidence. Only after all four jobs pass does the final job create the record and dry-run plan. Workflow permission is read-only and the file contains no tag, release, marketplace, manifest, or website mutation.

Validation and approval

assertCoordinatedRelease makes the JSON a real state machine rather than a bag of fields. Identity, stable RC lineage, artifact paths, application version, trust, approval, ordered receipts, and overall state must agree. The approval digest is computed from the immutable identity, candidates, trust evidence, and order. Changing any of those invalidates approval.

The existing Plugin publisher

plugin release publish now requires --release-record. Before it reaches the old confirmation and mutation logic, it inventories the workspace again and requires an approved, Developer-ID-notarized record for the exact selected tag and commit. Passing --yes skips a prompt; it does not skip policy.

Review hardening

Review caught two issues before pinning the boundary. The Ubuntu image did not include the workflow file read by a contract test. More importantly, stable lineage was checked at creation but not again when the record was read. Both are fixed, and negative tests now reject missing promotion evidence, contradictory progress state, and an artifact filename that escapes its workspace.

What this boundary proves

The full Plugin acceptance suite passes 116 Node tests and 94 Python tests; Desktop passes 62 tests; hosted Ubuntu and macOS matrices pass the pinned head. P5 therefore completes the deterministic model and dry-run preparation portion of R6.

What remains: P6 supplies real Developer ID and notarization evidence, P7 supplies the update and website surfaces, and P8 obtains exact approval and performs the first live convergence. R6 remains NOT YET until those public-path facts exist.
