GateReeve · PR #18 · P9 implementation

The same trusted app, now installable with Homebrew

This change adds a guarded way to publish a Cask for the exact signed, notarized, already-proven GateReeve DMG. It deliberately does not make CI the authority to create a public repository.

Background

GateReeve already has a public universal DMG whose bytes, Apple signature, notarization, staple, Gatekeeper result, and direct installation are known. The final distribution requirement is convenience: brew install --cask should install those same bytes—not a rebuild and not a bundle that quietly owns the Plugin or CLI.

Intuition

Trusted release record
→
Sealed Cask plan
→

→

Freedom lives inside the boundary: code may render, inspect, test, and retry. The public mutation occurs only when the plan digest the maintainer saw is the digest the command receives.

The generated artifact

cask "gatereeve" do
  version "0.1.0-rc.1"
  sha256 "9cbe51065692857ba929e153863fa92c8fe2dc4d275eb29453014a04e1f1ea92"
  url "https://github.com/TrentBrown/gatereeve/releases/download/v#{version}/GateReeve-#{version}-macos-universal.dmg"
  app "GateReeve.app"
end

The real renderer also supplies description, homepage, caveats, and cleanup metadata. The important invariants are the exact URL, exact checksum, and the single application payload.

Why the smoke test uses an upgrade

A fresh install proves Homebrew can mount the approved DMG and place the application. An upgrade proves the final rendered Cask participates correctly in Homebrew's lifecycle. Both phases verify bundle identity, Developer ID/Gatekeeper trust, and that the executable is universal.

Review results

  • All 15 hosted checks pass.
  • Native Cask install and upgrade pass on ARM and Intel.
  • The public tap remains absent and no publication mutation occurred.
  • Three pre-pin review findings—trust completeness, architecture evidence, and CLI/Desktop package boundaries—were corrected.

Quiz

1. Which bytes does the Cask install?

The checksum and URL bind the Cask to the already-proven public DMG.

2. What else does the Cask install?

The Plugin remains required but separately managed; the CLI remains optional and separately managed.

3. What authorizes public tap creation?

CI proves behavior but is not the authority for the distinct public mutation.

4. Why run on two macOS architectures?

Both jobs consume the same DMG; they verify native behavior on each platform family.

5. What happens after this PR merges?

Publication and the final public-tap smoke remain a separate controlled operation.
