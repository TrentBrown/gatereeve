A release protocol that can stop safely

PR #16 turns an approved, notarized candidate packet into a recoverable publication protocol. It does not publish the first RC. It makes the later, separately approved publication exact, observable, and safe to resume.

BackgroundIntuitionCodeQuiz

Background

GateReeve is distributed as related but independently installed products. The Plugin governs agent work. Desktop observes that work. A release must therefore coordinate two different public outcomes: the Plugin marketplace and a signed macOS companion. Previous slices already produced a universal DMG, established Apple trust, modeled ordered publication, and taught Desktop to read a fixed manifest.

The difficult part is not issuing five API calls. It is preserving one meaning across them. A tag may exist while a workflow is still running. A release may exist while an asset upload is incomplete. A manifest PR may be blocked by ordinary branch policy. A Pages deployment may lag behind its merge. Retrying must continue the same release, not create a plausible substitute.

The boundary: preparation may use protected CI and Apple credentials, but publication authority begins only after a human approves the exact version, source commit, artifact hashes, trust evidence, future manifest bytes, and plan digest.

Intuition

Think of the release record as a sealed packet plus a five-line ledger. The packet contains every byte whose identity matters. The ledger starts empty. Each adapter first asks, “Does the public world already contain exactly my approved result?” If yes, it records the receipt and moves on. If no, it creates only that result, verifies it, records the receipt, and moves on. Any disagreement is a stop.

This is convergence rather than rollback. Public history is immutable, so the safe response to interruption is to prove what already happened and continue. Deleting a tag or replacing an asset would destroy the very evidence recovery needs.

Why the manifest exists before approval

The website manifest contains a publication timestamp, but changing that timestamp during publication would change the file hash after approval. PR #16 therefore reserves the trusted packet’s creation time as publishedAt and generatedAt. The value means “this public candidate was sealed at this time.” It keeps the future manifest, checksum, and plan digest stable while remote surfaces converge.

Code walkthrough

1. Preparation seals the public outputs

desktop-release-manifest.js validates the same exact URL-free schema consumed by Desktop and the website. A release entry can be rendered only from complete Developer ID, hardened-runtime, secure-timestamp, notarization, stapling, and Gatekeeper evidence. coordinated-release.js writes the current manifest, future manifest, and SHA256SUMS into the immutable workspace, records their sizes and hashes, and rehashes them before publication.

2. Commander exposes an explicit approval surface

The new plugin release publish-coordinated command accepts exactly one mode. --dry-run performs remote reads and consistency checks without changing approval or public state. --confirm also requires an approver and the exact inspected plan SHA-256. The runbook keeps packet preparation, inspection, dry run, human approval, and confirmed publication visibly separate.

3. Adapters converge the ordered surfaces

Tagexact lightweight ref
Pluginwatch ordinary tag workflow
PrereleaseDMG + SHA256SUMS only
Manifest PRone commit · one path

The tag adapter refuses an existing tag aimed elsewhere. The Plugin adapter observes the established marketplace workflow rather than publishing through a second mechanism. The Desktop adapter accepts only the approved prerelease target and assets, including GitHub-computed digests, and rejects extras. The website adapter polls a fixed production URL with no credentials or referrer, rejects redirects, limits responses to 64 KiB, and succeeds only on byte-for-byte equality.

4. The manifest PR is transport, not another decision

github-publication.js derives one short-lived branch from release version and plan digest. Its PR body carries a machine-readable identity marker. Recovery checks the marker, head SHA, original base, commit parent, changed-file comparison, PR title, base, draft state, and file list. Only one generated commit changing the exact manifest path is allowed. GitHub must report the exact head clean and mergeable under ordinary policy. After merge, the adapter verifies main’s bytes and removes only the exact generated branch.
