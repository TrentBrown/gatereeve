GateReeve · PR #19 · Feature final

From “the Cask exists” to “the public command works”

The previous slice published an exact, approved Homebrew Cask. This final slice closes the last epistemic gap: clean Apple Silicon and Intel machines use the same command a real user will type, while the verifier checks the public instructions before allowing Homebrew to evaluate them.

Background

The product has three independent surfaces

Plugin

The governance system inside a supported coding agent. It is required, but its native manager owns installation and updates.

Desktop

An optional read-only observer. The Cask installs this application and nothing else.

CLI

An optional operator surface over the same protocol. It retains its own package lifecycle.

Release record

The immutable connective tissue: version, source commit, DMG hash, trust evidence, and publication receipts.

The public Cask points at the already-published universal DMG. It does not build another application. This lets a checksum prove that direct-DMG and Homebrew users receive the same bytes.

Key distinction: publishing a byte-identical Cask and testing a local copy are strong evidence, but neither literally exercises TrentBrown/gatereeve/gatereeve. PR #19 adds that last public-path observation.

Imagine the sealed packet says the Cask hash is 963f…ebb2. The runner clones the actual public tap and hashes the file Homebrew will read. Only if it also produces 963f…ebb2 does the test run the literal install command.

This ordering matters. A post-install comparison would tell us that unexpected instructions ran. A pre-install comparison prevents that execution and turns remote drift into a safe failure.

Code walkthrough

1. A second smoke mode reuses the same application proof

smoke-homebrew-cask.mjs already knew how to inspect an installed GateReeve application. The public mode reuses those checks but changes the acquisition path from a disposable local tap to the public tap.

brew tap TrentBrown/gatereeve
# compare cloned Casks/gatereeve.rb with the sealed packet
brew install --cask --appdir=<temporary> \
  TrentBrown/gatereeve/gatereeve

The runner refuses a pre-existing GateReeve installation or tap. Its evidence therefore describes a clean first installation, not an accidental reuse of machine state.

3. CI runs two complementary experiments

Local install and upgrade

Proves the exact Cask can enter and advance through Homebrew's lifecycle using the approved DMG bytes.

Proves the real tap identity and literal user command on clean ARM and Intel runners.

4. Final verification corrected a stale website assertion

The website test had been written when no RC existed and still required channels.rc to be null. Publication correctly changed the durable fixture. The test now requires the exact trusted v0.1.0-rc.1 metadata while continuing to assert the Plugin prerequisite and RC update explanation.

Quiz

1. Why does the public smoke explicitly tap before running the install command?

The fully qualified install could tap automatically, but explicit tapping creates a safe pre-execution inspection point.

2. What relationship does the Cask have to the direct DMG?

There is one application artifact; the Cask is a distribution instruction for those same bytes.

3. Why are there both local upgrade and public install jobs?

The experiments answer different questions without giving the Cask ownership of other components.

4. What made the old website assertion stale?

The product state advanced legitimately; the test was still describing the pre-publication world.

5. What does the Cask deliberately leave alone?

The hybrid distribution model keeps each native manager authoritative for its own component.
