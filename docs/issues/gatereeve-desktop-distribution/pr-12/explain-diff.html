GateReeve engineering note

Making the signing key visible

PR #12 fixes the narrow boundary between an imported Developer ID identity and the macOS process that actually signs GateReeve.

Contents: BackgroundIntuitionCodeQuiz

Background

The beginner's version

A macOS signing identity is a certificate paired with a private key. GateReeve imports that pair into a temporary keychain on a protected GitHub runner. The keychain is a container; the user keychain search list tells macOS which containers participate in ordinary identity lookup.

The first protected rehearsal proved the contents were correct. The certificate imported, its private key was usable, and an explicit identity check found the expected Developer ID. Yet Electron later passed the identity fingerprint to codesign, which could not finish the lookup.

The specific boundary

Electron constrained signing to the temporary keychain, but macOS still needed that keychain in the user's active search list while resolving the private-key item behind the certificate fingerprint. PR #12 makes both constraints agree.

Intuition

Imagine a library with a correct catalog card and a locked archive box. Pointing at the box proves where the document should be, but the librarian's active catalog must still include that archive. The fix temporarily adds the archive to the catalog, does the work, and restores the catalog exactly.

Key idea: temporary access should be additive and reversible. GateReeve does not replace the runner's normal keychains or install credentials into its login keychain.

Code

1. Capture before mutation

The import step writes the current user search list to a runner-temporary file. Its path is carried to the unconditional cleanup step; no credential content is logged.

2. Prepend the isolated identity store

After certificate import and partition authorization, Bash parses the quoted keychain paths into an array. The temporary keychain becomes the first search target, while every original entry remains available. Electron also keeps receiving the explicit temporary keychain path.

3. Restore before deletion

The always() cleanup reconstructs the captured list before deleting the temporary keychain and certificate files. This ordering avoids leaving a deleted keychain in the runner's active list.

4. Pin the contract

The coordinated-workflow test now requires the setup and restoration commands. Feature records connect the live failure, I-9, the decision, and the required post-merge rehearsal.
