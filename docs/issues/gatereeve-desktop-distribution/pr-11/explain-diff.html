From a buildable DMG to verifiable Apple trust

PR #11 adds the protected, nonpublishing boundary that can turn GateReeve's already universal development package into a Developer ID-signed, notarized, stapled, Gatekeeper-accepted candidate.

Background

The beginner's version

A macOS application can be structurally correct yet still look untrustworthy to a user's Mac. Developer ID signing says who produced the application. Hardened runtime constrains it in ways Apple expects. Notarization asks Apple's automated service to inspect a submitted package. Stapling attaches the resulting ticket to the downloadable file, and Gatekeeper assessment checks the experience macOS will apply when a user opens it.

These claims must refer to one exact file. If a DMG is notarized and then altered, the old result says nothing about the new bytes. That is why this change records the filename, byte count, SHA-256 digest, source commit, release tag, signing identity, team, notarization ID, and the results of stapler and Gatekeeper.

The GateReeve context

Earlier slices already produced one universal DMG, ran its contained application on Apple Silicon and Intel, and coordinated Plugin and Desktop candidates under one recoverable release record. That record deliberately described the existing package as development-ad-hoc. Public publication rejected it.

Safety invariant. This PR prepares trust evidence but grants no publication authority. The protected job has read-only repository permissions and emits temporary workflow artifacts only.

Intuition

The core idea is a chain of custody. Cheap, unprotected jobs first build and test candidates. A protected job receives Apple credentials only after those checks and human environment approval. It rebuilds the same pinned version, signs and notarizes it, and emits exact-byte evidence. Two fresh native runners then distrust the claim and verify it independently before the coordinated record accepts it.

For example, suppose the trusted DMG digest is abc…123. Both native verification records must name abc…123, the same notarization ID, and the same Developer ID team. One record naming def…456 makes coordination fail. Likewise, even a perfectly trusted record remains unpublishable until a later explicit approval matches the digest of its complete publication plan.

Code walkthrough

1. Trust facts become a strict contract

apple-trust-contract.mjs validates protected configuration and the evidence schema. It parses real codesign output instead of accepting a caller's assertion. The coordinated form is deliberately redundant: a status alone is insufficient; every boolean fact and the ordered evidence labels must agree.

developer-id-notarized
  identity + team ID
  hardened runtime + secure timestamp
  accepted notarization ID
  validated staple
  accepted Gatekeeper assessment

2. Packaging has two explicit modes

The ordinary package remains ad-hoc signed for repeatable PR testing. Supplying a Developer ID identity changes Electron Packager to hardened-runtime signing and passes the ephemeral keychain. The finished DMG itself is also signed and timestamped.

3. The notarization script proves before it records

notarize-macos.mjs verifies both app and disk-image signatures, compares their authority and team with protected configuration, submits the DMG through the App Store Connect team key, waits for Accepted, staples, validates, and runs spctl. Only then does it hash the DMG and write evidence.

4. The workflow isolates credentials

The desktop-trust job references the release-publication environment with deployment: false. Credentials are decoded into runner-temporary files, the certificate enters a newly created keychain, and an unconditional final step removes both. Downstream jobs receive the DMG and non-secret evidence, never the keys.

5. Native verification closes the loop

Apple Silicon and Intel jobs download the same trusted artifact. Each repeats codesign, staple, Gatekeeper, universal-binary, package-content, version, and governed-fixture runtime checks. The release-record builder rejects mismatched bytes, architectures, versions, or trust facts.

6. The runbook captures the human half

The setup guide covers individual enrollment, a fresh CSR for each certificate, Developer ID Application rather than Installer, the G2 intermediate chain, login-keychain pairing, team API key authentication, encrypted recovery, protected GitHub values, rehearsal, rotation, and restoration. These details reflect the process actually completed for this repository.
