Knowing that a release exists, without becoming an updater

This change gives GateReeve Desktop a deliberately narrow release sense: it can discover a trusted newer version and point to its official page, but it cannot fetch, replace, restart, or install the application.

BackgroundIntuitionCodeQuiz

Background

GateReeve has three independently installed pieces. The Plugin governs work inside an agent. The optional CLI exposes the same protocol to a terminal. Desktop is a read-only observer. That separation matters here: update discovery belongs to the Desktop product, not to a selected feature record and not to the governance state machine.

Before this PR, Desktop could notify about workflow events—failed gates, stale evidence, human review, merges—but knew nothing about releases of itself. The release pipeline already reserved two later public surfaces, updateManifest and earlyAccessWebsite. PR #15 builds their private consumers and checked-in inactive state. It does not publish either surface.

The invariant: an empty manifest is valid. Until a trusted GitHub prerelease exists, the correct website behavior is not a broken link or a speculative download. It is no link at all.

Intuition

Think of the manifest as a small notice board with exactly two slots: latest stable and latest RC. It contains evidence, not instructions. There is no URL in either slot. The application already knows the one project endpoint it may read and the one GitHub repository it may open.

{
  "schemaVersion": 1,
  "product": "gatereeve-desktop",
  "generatedAt": null,
  "channels": { "stable": null, "rc": null }

Code walkthrough

1. The manifest is strict and URL-free

update-manifest.js parses only stable and rc.N versions. A non-null release must match its channel, exact DMG filename, byte size, SHA-256, full source commit, publication time, and all six Apple-trust facts. Exact-key validation rejects hidden extension fields, including a manifest-controlled URL.

2. Transport has hard edges

update-client.js performs one GET to the fixed Pages endpoint. It sends no credentials, referrer, identifier, worktree fact, or dynamic query. Redirects fail. A referenced ten-second timer guarantees termination even in a minimal Node host; streamed bytes are cancelled past 64 KiB.

3. Cache and coordination stay outside workflow state

update-cache.js writes an atomic mode-0600 update-cache.json under Electron user data. update-coordinator.js loads it, publishes a cached projection immediately, and starts stale automatic work without awaiting it. Manual checks bypass freshness. The current release version comes from staged compatibility metadata, because macOS bundle display versions may strip -rc.N.

4. Electron exposes only named update actions

The main process adds validated IPC for reading update state, requesting a manual check, and opening the derived official tag page. Preload mirrors those narrow calls. There is no file download, installer, updater, restart, arbitrary URL, or process-execution surface.

5. Notification has two layers

The in-app banner ignores the native-notification preference and is always shown for an available version. Native delivery remains opt-in and records the last notified version in the update cache, preventing repeated alerts after relaunch.

6. Early Access starts visibly inactive

The website now explains that the Plugin is required and Desktop is optional. Its release link is checked in without an href and hidden. desktop-early-access.js activates it only from a trusted RC entry and derives the same exact GitHub tag page. P8 will later publish that manifest after the prerelease surface is durable.
