Deterministic passage, agentic work

This change gives GateReeve a durable, versioned protocol for feature, slice, change, and PR-boundary state. Agents remain free to reason and implement, but they must pass through explicit guards before the workflow record moves.

Contents: Background Intuition Code walkthrough Review remediation Quiz

Background

Before this PR, GateReeve described a careful software-development process through skills, documents, and deterministic validators. That was already useful, but the durable record did not itself know whether a feature was designing, implementing a slice, waiting at a boundary, or carrying stale evidence. An agent could follow the process well, yet the process had no single protocol object capable of rejecting an illegal passage.

Three kinds of truth

Recorded

Decisions and passages belong in an append-only journal: design approved, slice started, gate passed, change applied.

Inferred

Git SHAs, PR facts, artifact hashes, validator output, and merge content are read fresh from their authorities.

Derived

Current state, blockers, eligibility, and freshness are replayed from the journal plus current facts.

The distinction matters. GateReeve does not write a mutable state.json that can drift from history. It pins the workflow model, appends events, and reconstructs the projection. Nor does it become a workflow engine: it does not schedule agents, run retries, stage code, or commit files.

Compatibility rule. New features initialize governance. Existing feature folders without the model lock and journal are reported as legacy and may finish without reconstruction.

Intuition

Think of the protocol as a railway signal system. The agent drives the train: it chooses speed, investigates the route, and handles surprises. GateReeve controls only the signal between durable blocks. A green signal records why passage was safe; a red signal reports exactly what is missing.

A concrete freshness example

Suppose verification passed for source abc123. The result stores a fingerprint over the model, attempt, gate, and its inputs. If the source becomes def456, the old outcome remains historically visible as PASS, but its derived freshness becomes STALE. Dependents stop being eligible until the changed evidence is rerun.

Important edge case. The merge transition rechecks the active boundary fingerprints. Passing into human review is not a permanent freshness exemption; changed evidence must still fail closed before GateReeve records the merge.

Code walkthrough

Canonical protocol core

plugin-src/shared/resources/protocol/ owns model validation, storage, journals, replay, transitions, boundary gates, changes, observers, and graphs.

Pinned model

workflow-model.json declares the closed state vocabulary, authorities, trusted guard IDs, gate DAG, scope routing, and invalidation rules.

Durable feature record

Initialization atomically creates workflow-model.lock.json, events.jsonl, and interview.md. Partial initialization is removed.

Replay and mutation

Every append re-reads and validates sequence and model history under an exclusive lock. Rejected operations append nothing.

Optional Commander CLI

gatereeve exposes status, next, history, graph, checks, and semantic feature/slice/gate/change commands over the same plugin adapter.

Native packaging

Codex and Claude packages receive identical canonical resources. The standalone npm package stages the complete resource tree during prepack.

Merge proof

The Python verifier accepts ancestry when available, or compares exact Git tree entries for every reviewed path after squash or rebase.

Operational visibility

SessionStart reports governed, legacy, missing, or inconsistent mode. The documentation site visualizes feature and slice lifecycles.

The adapter does not expose a generic “set state” command. The request names a semantic operation. The core loads the pinned model, rebuilds the projection, checks authority and guards, and then either appends one normalized event or returns a stable failure envelope.

Model migration

An active feature does not silently inherit a new plugin model. Migration first produces an impact report. Human confirmation then writes a transaction marker before replacing the lock and journal. If the process is interrupted between those two file replacements, ordinary reads fail closed and recovery deterministically rolls forward.

Review remediation

The first pinned review found three gaps. Each was fixed before the final boundary was repinned.

  1. Post-review freshness: merge passage now requires a fresh fingerprint projection of the active boundary attempt.
  2. Executable next actions: boundary suggestions now use the actual command family and include attempt identity.
  3. Canonical source precedence: source checkouts prefer plugin resources; installed CLI packages fall back to their generated staged copy.

Focused regressions accompany each repair, and the complete 95-test JavaScript suite plus 94 Python tests pass on the final source.
