Verified Homebrew Cask upgrades

PR #23 turns a valid existing GateReeve Cask from an accidental blocker into a narrowly verified predecessor, without weakening the publisher's overwrite protection.

Contents: Background · Intuition · Code · Quiz

Background

A Homebrew Cask is a small Ruby file that names an application version, a download URL, and the SHA-256 digest Homebrew must see. GateReeve generates those bytes from an already signed and notarized coordinated release. The Cask publisher never rebuilds the DMG.

Before this change, publication was idempotent only when the public Cask already contained the target bytes. That was safe for retrying one release, but it rejected every normal upgrade because an older release necessarily has different bytes.

The constraint: accept the existing rc.1 Cask for an rc.2 upgrade, but do not accept arbitrary content merely because it is older-looking.

Intuition

The new preflight recognizes exactly two safe states:

Read tap
Fetch Casks/gatereeve.rb
Classify
Exact target or predecessor
Verify
Canonical bytes + older SemVer + public asset digest
Proceed
Dry-run or exact PR publication

If the bytes are already the target, recovery remains idempotent. Otherwise, GateReeve extracts only the version and digest, regenerates the entire expected Cask, and demands byte-for-byte equality. It then proves that the version has lower SemVer precedence and that a non-draft GitHub release exposes the named DMG with the same digest.

rc.1 canonical bytes + rc.1 public DMG digest → safe predecessor
rc.2 different bytes while targeting rc.2       → reject equal version
rc.3 while targeting rc.2                       → reject newer version
rc.1 with another homepage or URL               → reject noncanonical
rc.1 backed only by a draft release             → reject nonpublic

Code walkthrough

1. One canonical renderer

The Cask renderer now has an identity-level core. Release preparation and predecessor validation therefore compare against the same template instead of maintaining two interpretations.

2. Exact SemVer precedence

Base and prerelease numeric identifiers use BigInt. This matters because SemVer permits integers beyond JavaScript's safe-number range. Build metadata remains correctly irrelevant to precedence.

3. Public predecessor proof

The preflight accepts differing public-tap bytes only after canonical rendering, strict older-version comparison, non-draft release verification, and matching asset digest. Any failure occurs before the publisher creates or merges a tap pull request.

4. Evidence and tests

Ten focused tests cover valid upgrades, arbitrary-precision identifiers, malformed and reordered states, release mismatch, draft rejection, exact approved mutation, and packet tampering. The real rc.2 packet also passes a live read-only dry run against the rc.1 tap.
