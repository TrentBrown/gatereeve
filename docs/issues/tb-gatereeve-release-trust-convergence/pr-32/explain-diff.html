Background

GateReeve already knows how to build, sign, notarize, staple, verify, and distribute its universal macOS DMG. The missing contract is not another packaging engine. It is durable proof that every later action refers to the same source, candidate version, exact bytes, Apple request, and approved sequence of release stages.

What stays GateReeve-specific

One universal DMG, coordinated Plugin/Desktop releases, and the existing Homebrew Cask surface.

Not in this slice: protected GitHub environments, hosted trust production, native ARM/Intel evidence workflows, sealed publication planning, or public release mutation. Those depend on these records and arrive in later governed slices.

Intuition

1. A release is an append-only receipt book

Schema v2 replaces an ambiguous current-state view with an ordered prefix of product-specific stages. Each entry hashes its evidence and the preceding entry. The record may advance exactly one stage, but it cannot skip, reorder, duplicate, or rewrite history.

source-pinnedrepository + SHA + tag
→
candidate-qualifiedbytes may be bound
→
trusted universal DMGsame bound bytes
→
native + desktop verifiedstructured evidence
→
approved + publishedlater slices

The complete list contains twelve stages, including GateReeve’s universal Desktop and Plugin coordination points. Semantic conformance does not mean copying PortReeve’s two-architecture DMG graph.

2. An Apple attempt is not a successful release stage

A notarization submission may time out, be rejected, or become ambiguous because a runner disappeared after Apple received bytes. Those are durable operational facts—not successful trust milestones.

Release lifecycle

Records completed product gates. It consumes an accepted attempt only when source, version, tag, and artifact identity all match.

⇄
Notarization attempt

Records prepared, submitting, uncertain, submitted, polling, timeout, accepted, rejected, and superseded states.

3. Recovery follows the request, not the workflow run

If execution ends while submission is ambiguous, recovery reconciles retained candidate identity with Apple history. It does not blindly submit again. Changed bytes require a fresh candidate version and a linked superseding attempt.

The validator cross-checks materialized summaries against the append-only history, including request identity, reconciliation, polling sessions, supersession, timestamps, and allowed transitions. A forged summary without matching history fails.

The macOS script persists before risky edges

apps/desktop/scripts/notarize-macos.mjs writes records atomically, changes to submitting before calling notarytool submit, records the returned UUID before polling, and uses notarytool info to resume a retained request. Every status response must name the same request ID.

Reviewer focus

  1. Confirm every successful lifecycle transition is a strict ordered append and remains GateReeve-specific.
  2. Confirm Apple attempts cannot be mistaken for completed trust stages.
  3. Confirm ambiguous submission requires reconciliation and cannot silently produce a duplicate request.
  4. Confirm candidate source tag, semantic version, commit, filename, byte length, and SHA-256 remain exact across recovery.
  5. Confirm v1 released history is inspectable but not mutated through v2 helpers.
