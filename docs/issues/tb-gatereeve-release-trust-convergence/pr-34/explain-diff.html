Background

The beginner’s version: signing is not publication

A release crosses several different authority boundaries. Building creates bytes. Developer ID signing says who produced them. Apple notarization records Apple’s acceptance. Stapling attaches that result to the distributable DMG. Native Gatekeeper checks prove that both Apple Silicon and Intel hosts accept the same universal artifact. Publication then changes public systems: a tag, Plugin marketplace branch, GitHub prerelease, update manifest, website, and eventually a Homebrew Cask.

Those steps should not share one all-powerful credential. A signing job should be unable to publish, and a publishing job should be unable to rebuild or sign. Otherwise an approval intended for one action silently authorizes another.

Trust production

Uses Apple credentials, creates the final notarized universal DMG, and emits native ARM64/Intel evidence.

Cannot: create tags, releases, marketplace updates, manifest PRs, website changes, or Cask PRs.

Publication

Consumes retained exact bytes plus a reviewed plan digest and converges public surfaces.

Cannot: build, sign, notarize, staple, or replace trusted bytes.

The system before this PR

Earlier slices established schema-v2 lifecycle stages, durable notarization attempts, protected Apple production, and independent native evidence. GateReeve also already had deterministic repository-local adapters for publishing the Plugin, Desktop assets, update metadata, website state, and Cask. The missing piece was a hosted authority that sealed those existing transports behind the schema-v2 record and separate approval environments.

Load-bearing distinction: the old adapters remain useful mechanisms. They are no longer the authority to invent a plan. The schema-v2 packet and protected hosted workflow are the authority; adapters may only converge to that exact plan.

Core intuition

Imagine a tamper-evident shipping manifest. The warehouse lists every box by weight and fingerprint, seals the manifest, and hands both to a courier. The courier may deliver missing boxes and record receipts, but may not repack them or edit the manifest. A retry checks which exact boxes already arrived and continues from the first missing receipt.

If the process stops after the Desktop prerelease, a retry does not rebuild anything. It first proves that the tag, marketplace, and prerelease already match the sealed record. It then resumes at the update manifest. If any completed surface differs, recovery fails closed.

Code walkthrough

1. Finalize v2

hosted-publication-v2.js verifies the lifecycle ends exactly at Desktop trust, inventories the Plugin tree, checks final DMG and both native documents, derives checksums/manifest, and appends distribution-finalized.

2. Seal a plan

The packet stores exact inputs and outputs plus publication-plan.md. Re-rendering must produce identical bytes and the same SHA-256.

3. Publish in order

The hosted publisher preflights all five surfaces, records an approval bound to the plan digest, converges one surface at a time, and atomically appends its receipt.

4. Link Cask later

homebrew-cask-v2.js requires primary published, binds its record/stage/plan/receipt digests, and adds exact public-DMG install and launch evidence.

Why the v1 projection exists

The mature transport adapters expect the historical coordinated-record shape. The new code constructs that shape in memory from immutable v2 stages and validates it with the old reader. It does not write a synthetic mutable v1 history. This lets GateReeve reuse proven product-specific transports without weakening the new authority model.

The marketplace rollback guard

Directly publishing retained Plugin bytes is necessary because a tag created with GitHub’s workflow token does not start another tag workflow. Direct transport is safe only if it cannot overwrite newer history. The new semantic version comparison therefore accepts either the exact completed target or a strict successor to the deployed marketplace release; equal-different and newer deployments fail.

Tap PR partially completedSelf-identifying branch/PR and exact Cask digestRetry converges to the same PR or verifies the already merged bytes
What recovery never means: rerun a trust job that rebuilds bytes, change the plan digest, resubmit a notarization request without evidence, force an older marketplace version, or reuse a candidate version after Apple-bound byte drift.

Conformance with PortReeve

The two products now share the same semantic spine: immutable source, exact-byte authority, explicit lifecycle stages, protected trust production, independent native Apple evidence, separated publication approval, sealed plans, bounded recovery, ordered receipts, and immutable published history.

They intentionally do not share an artifact graph. GateReeve keeps one universal DMG and coordinated Plugin/Desktop/Cask surfaces. PortReeve keeps architecture-specific DMGs and native CLI surfaces. Conformance means equivalent guarantees at matching boundaries, not identical files, runners, or runtime code.
