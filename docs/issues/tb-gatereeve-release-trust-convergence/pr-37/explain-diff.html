GateReeve · PR #37 · pinned review

The approval gate existed in configuration, but the jobs walked around it.

This correction removes one misleading setting from six protected jobs. The result is that GitHub creates a deployment, pauses for the configured reviewer, and retains the approval record before releasing trust or publication authority.

Contents: Background Intuition Code Quiz

Background

The beginner's model: a protected job is a temporary capability grant

GateReeve stores Apple signing credentials in release-trust and publication authority in release-publication. A job names one of those environments when it needs that capability. GitHub's environment protection rule is meant to pause the job, show the proposed deployment to a reviewer, and expose the environment's secrets only after approval.

1

Reviewed main

Exact source SHA and candidate identity.

2

Deployment wait

Reviewer inspects and approves the protected job.

3

Trust work

Ephemeral Apple credentials sign and notarize exact bytes.

4

Evidence

Approval and artifact history remain auditable.

The narrow defect

The workflows named the correct environments but also set deployment: false. The RC.3 rehearsal proved that signing, notarization, stapling, Gatekeeper assessment, and native verification all worked. Yet GitHub created no pending deployment and no deployment record, so the configured required reviewer never participated.

Before

environment:
  name: release-trust
  deployment: false

The job could use environment material without producing the required deployment/reviewer evidence.

After

environment:
  name: release-trust

GitHub follows the normal environment-deployment path, where the configured protection rule can pause and record approval.

Two facts remain separate. RC.3 is valid Apple and native trust evidence for its immutable bytes. It is not valid evidence that a human reviewer authorized access at the protected boundary.

Intuition

Think of the environment as a locked tool cabinet and the deployment as the checkout slip. Naming the cabinet identifies which tools a job wants. The checkout slip is what routes the request to an approver and leaves an audit trail. The old setting effectively said, “use this cabinet, but do not create a checkout.” PR #37 removes that exception.

Exact packet

Source, Plugin, universal DMG, native evidence, and plan digests.

release-trust

Apple credentials only. Cannot publish.

Sealed record

Trusted bytes and evidence, unchanged downstream.

release-publication

Publication authority only. Cannot sign or rebuild.

The fix applies symmetrically to six jobs: initial trust production, bounded trust recovery, primary dry run, primary publication, Cask dry run, and Cask publication. It does not merge those authorities. It makes each existing boundary real.

Code walkthrough

1. Restore deployment creation

Four workflow files lose six deployment: false lines. Names, permissions, source checks, concurrency, artifact transport, dry-run separation, and exact-plan behavior remain unchanged.

  • coordinated-release-prepare.yml: protected Apple trust production.
  • coordinated-release-trust-recover.yml: same-byte, same-request recovery.
  • coordinated-release-publish.yml: primary rehearsal and publication.
  • homebrew-cask-publish.yml: linked Cask rehearsal and publication.

2. Turn the defect into a regression contract

The workflow tests now require the expected environment name and independently reject deployment suppression. Checking both matters: merely deleting the environment would also make deployment: false disappear, but would be even less protected.

assert.match(workflow, /environment:\n\s+name: release-trust/);
assert.doesNotMatch(workflow, /deployment:\s*false/);

3. Make operators verify the live fact

The setup and release guides now say that a protected run without a pending deployment or recorded approval is blocking. This is defense in depth: repository tests protect the declaration; the operator checks GitHub's actual enforcement.

4. Preserve candidate and publication safety

The correction does not rerun RC.3, reinterpret its absent approval, or publish anything. After merge, a fresh RC identity must demonstrate the wait. Only then may the bounded credential overlap be removed and final nonpublishing acceptance resume.
