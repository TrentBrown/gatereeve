One release, one conductor

GateReeve used to ask its operator to stitch together several GitHub workflows and carry run IDs and digests from one phase to the next. This change turns those phases into instruments played by one conductor: a single start or resume operation, backed by an immutable chain of evidence.

Background

The release is really two linked publications

GateReeve ships a signed, notarized Desktop disk image and native workflow-plugin packages. After the primary release is public, a Homebrew Cask must be generated from the exact public DMG, published separately, and tested both through the retained record and the literal public tap. Those steps deliberately have different authority boundaries.

Reviewed main
Apple trust
Primary publish
Human install
Cask publish
Public smoke

Previously, each phase was independently dispatchable. The security checks were strong, but the operator had to know which workflow came next and transcribe internal identities. That was slow and created a second problem: the runbook itself became part of the control plane.

Key distinction: orchestration does not mean collapsing authority. The conductor automates clerical transitions while protected environments still stop immediately before Apple credentials or public mutation.

Intuition

Think of the release as an append-only ledger. A checkpoint says, “for tag v0.1.0-rc.9, source commit abc… has reached stage X using evidence Y.” The next checkpoint contains the SHA-256 of the previous one. A resume operation does not ask the operator where to continue; it downloads every checkpoint whose artifact name belongs to that tag, verifies the chain, and follows the one legal next edge.

INITIALIZED
  → TRUST_PENDING
  → TRUSTED
  → PRIMARY_FINALIZED
  → PRIMARY_REHEARSED
  → PRIMARY_PUBLISHED
  → WAITING_FOR_DIRECT_INSTALL
  → CASK_FINALIZED
  → CASK_REHEARSED
  → CASK_PUBLISHED
  → SMOKE_VERIFIED
  → COMPLETE

A failed attempt appends a record at the same stage. It never pretends that authority advanced. If retry is safe, its next action is RESUME; an immutable conflict instead says BURN_RC.

The direct-install pause is different. GitHub cannot prove that a person launched the public DMG. The first run therefore stops at an honest waiting state. The operator installs it, then selects resume with one checkbox. GateReeve records the authenticated GitHub actor, time, and exact DMG digest, then carries the Cask chain to completion automatically.

Code walkthrough

1. One trusted workflow entry

.github/workflows/release-conductor.yml is the sole manual production trigger. Both operations require their workflow implementation to be the exact current main commit. Start additionally rejects reused tags and version disagreement before a protected job can run. Resume identifies a release by tag alone.

2. Reusable phases, preserved boundaries

The former manual preparation, recovery, finalization, publication, Cask, and smoke workflows now expose workflow_call. Read-only rehearsals run automatically without environments. Apple trust and the two publication operations retain protected deployments and only the permissions they need.

3. A strict state contract

release-conductor-state.js defines exact record keys, legal stages, required cumulative evidence, and passage rules. release-conductor-artifact.js writes canonical state, the full chain, a checksum, JSON status, and Markdown summary. release-conductor-discovery.js binds each retained artifact to a completed mainline conductor run and rejects gaps or divergent sequence numbers.

4. Failure remains resumable

The local composite action appends and uploads one immutable checkpoint. Every invocation uses a fresh temporary directory, including a failure record that repeats the current stage. This matters because preserving the failed attempt is what lets a later run recover without rebuilding trusted bytes.

5. Manual mutation paths are gone

The tag-triggered publisher and low-level workflow dispatches are removed. Old local publish, schema-v1 primary publication, and schema-v1 Cask publication commands are no longer in the command tree. The hosted mutation commands needed by reusable workflows refuse confirmation unless they are running inside the dispatched Release Conductor.

6. Smaller and quieter infrastructure

Official actions move to Node-24-compatible majors, jobs use Node 24, and the exact-Node-23 qp-cli-core dependency is replaced by direct Commander plus a small local help-tree renderer. Full CI ignores only the sealed Desktop metadata file, while the publication code still rejects any PR containing an extra path or altered byte.

7. Rehearsal provenance stays distinct from production

Until the first conductor release exists, pull-request Cask smoke uses the pinned last successful legacy publication artifact for read-only regression testing. The event-specific guard does not broaden production: a workflow_call still accepts only Release Conductor provenance. Container acceptance is likewise hermetic: it copies the workflow contract it reads and creates a tiny Git repository for ancestry tests instead of importing the host checkout’s .git directory.

8. Review evidence no longer rebuilds the product

A pull request is a cumulative diff, so ordinary path filters kept seeing the feature source even when the newest commit changed only review records. The new scope action examines the synchronize event’s exact predecessor-to-current delta. It accepts only a narrow lifecycle-artifact allowlist, then asks GitHub whether the same workflow succeeded for that exact predecessor SHA. Missing success, an unknown path, a requirement or plan change, or a non-ancestral update all choose the full matrix.

This forms a transitive chain back to real product coverage. It cannot turn a failing source head green by omission. Superseded work is cancelled only within a pull-request group; main and reusable release calls use their unique run IDs. BuildKit exports per-Ubuntu caches, and a locked npm cache mount accelerates deterministic npm ci layers.

9. DMG verification distinguishes contention from corruption

Both DMG verification call sites now share one small retry helper. It retries only Apple’s literal Resource temporarily unavailable result, at most three attempts with one- and two-second backoff. A checksum mismatch, invalid image, signature failure, or any other error is returned immediately; the last transient attempt also preserves the original error.
