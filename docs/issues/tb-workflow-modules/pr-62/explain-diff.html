1. Background

The beginner’s version: three kinds of truth

A GateReeve project has three different things that are easy to confuse. The project policy says which modules future work should use. A feature’s model lock pins the exact graph that governs that feature. A boundary attempt records actual outcomes and evidence for one PR. Changing a checkbox is therefore more consequential than hiding a card: it proposes a new project policy and may require an explicit feature-model migration.

Project policytracked selection for the project
→
Feature lockexact graph and model hash
→
Attemptpinned gates, outcomes, evidence

Before this PR, GateReeve could read and display the feature journal but had almost no workflow mutation surface. The new controls relax that posture narrowly. The renderer may ask to preview a complete list of enabled module IDs or request a waiver. It still cannot choose arbitrary files, submit event JSON, select an executable, or call a general protocol transition.

The screen must follow the workflow, not compete with it

The top rail remains the same six lifecycle states. Module detail appears below the state to which it belongs. Selecting Implementing shows slices and the selected PR attempt. Selecting Finalizing shows enabled finalization modules, if any.

2. Intuition

Checkboxes prepare a transaction

Suppose a project has three modules. A is locked. B depends on A. C depends on B. Enabling C visibly stages B and A. Disabling B does not secretly turn off C; GateReeve explains the conflict and offers to stage the dependent removal.

Draft choiceenable C
→
Closure previewalso stage A and B
→
Migration previewshow model/gate impact
→
Explicit applywrite policy; migrate if confirmed

This is why the UI sends the whole enabled-ID set rather than a command like “toggle C.” The main process rereads canonical definitions and policy, recomputes the graph, and refuses a stale or incomplete proposal.

A waiver is not a disabled module

Project checkbox

Durably changes which modules govern future attempts after validated adoption. It is configuration.

Skip for this boundary…

Records reasoned human risk acceptance against one active attempt and input fingerprint. It is evidence.

Changed inputs make the waiver stale. Locked modules never offer the action. Feature-scoped waivers are intentionally absent until the finalization slice creates an attempt and merge-input fingerprint to bind them to.

Why the packaged Python guard exists

The first review attempt exposed a real distribution bug: the new Desktop waiver path called a trusted Python guard that was not in the packaged application. The repair stages only pr_context.py and its two local dependencies, discovers compatible Python plus Git and GitHub CLI paths, and checks that the PR’s local and remote head still match the pinned source.

Desktop request
  → private pinned-context file
  → discovered Python 3.10+
  → canonical pr_context.py check-current
  → explicit Git and gh executables
  → protocol-core waiver validation
  → private file removed in finally
Bounded power: project manifests still cannot name this script or choose an executable. It is a built-in trusted guard reached only through the named waiver operation.

3. Code walkthrough

Exact evaluated range: cb85c672e6090f0286159b9897eacee9c3edf8fc..53f9babd3aaec06449eeb0c8fd7deb4ab143544b.

Policy manager

apps/desktop/main/module-policy.js owns inspection, preview, and apply. It builds a complete catalog from bundled and project definitions, checks exact requested IDs, computes hard-dependency closure, reports transitive dependents, resolves through the canonical graph validator, and refuses newly enabled modules whose local implementation is unavailable.

The apply path re-runs the preview, requires visible dependency additions to be accepted, requires a human label when the active feature must migrate, refuses symlink targets, writes a create-once temporary file, and atomically renames it to .gatereeve/workflow.json. It does not call Git.

Closed snapshot vocabulary

The canonical snapshot validator now inventories modules by the two legal slots, rejects duplicate IDs or slot drift, requires a readiness entry for every module, and admits only pendingrunningwaitingblockedunavailable as live states. This keeps future providers flexible without letting them invent workflow outcomes.
