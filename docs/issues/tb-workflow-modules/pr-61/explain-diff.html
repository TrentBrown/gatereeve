1. Background

The beginner’s version: events, models, and projection

GateReeve does not store “the current workflow” as one mutable status record. It stores an append-only event journal: design approved, slice started, boundary gate passed, and so forth. A versioned workflow model says which transitions and guards are legal. A projector folds the events into the current feature, slice, attempt, and gate state.

A PR boundary was already a dependency graph: pin context, reconcile documents, verify, evaluate in parallel, triage decisions, explain the diff, and validate the packet. Before this PR, that inventory lived directly in boundary.gates and its separate scope-routing table.

Invariant retained: human review is still a lifecycle passage, not a module. It becomes available only when every enabled required gate has a fresh, nonblocking outcome.

The narrower problem

Hardcoding made every project inherit the same check inventory and made a future post-merge build or release step look like a GateReeve core concept. The desired architecture needs project-specific checks, but it must not permit repository JSON to inject UI code or silently execute programs.

Fixed core

Feature and slice state machines, transition authority, trusted guards, fingerprints, evidence, and passage rules.

Extensible slots

boundary.evaluation for PR checks and feature.finalization for post-merge obligations.

2. Intuition

Think of a module as a sealed job description, not as loaded application code. It has a durable name, exact version and digest, dependencies, evidence rules, and optional pointers to a known skill, explicit manual step, command, or separately installed observation provider.

{
  "id": "example/license-audit",
  "version": "1.0.0",
  "digest": "sha256:…",
  "slot": "boundary.evaluation",
  "dependsOn": ["gatereeve/verification"],
  "observe": {
    "providerId": "example/license-provider",
    "version": "1.0.0"
  }
}

The tracked policy acts like a lockfile selector. It names the exact definitions a project wants and whether configurable ones are enabled. Resolution combines built-ins and project manifests, verifies all identities and digests, rejects unsafe graphs, and produces a deterministic topological order.

Hard dependency versus conditional order

dependsOn says “I cannot function without that module,” so an enabled module makes its hard dependency mandatory. after says “if that module is enabled, wait for it.” Decision Triage uses the latter for Judge and Code Review: it remains locked, but a project may later disable either review without making the graph invalid.

Toy example: if Judge is enabled, Decision Triage follows it and binds to its event. If Judge is disabled, the edge disappears; GateReeve does not manufacture a fake NOT_APPLICABLE result.

Why pin twice?

The full graph is pinned in the feature model so an installed update cannot alter the feature accidentally. A copy is also pinned on every new boundary attempt. That second pin matters when the user explicitly migrates the feature later: old attempts must still say which modules and versions governed their evidence.

Attempt Agraph v1 · Judge enabled
→
Explicit migrationnew model hash; prior boundary snapshot retained
→
Attempt Bgraph v2 · Judge disabled

Attempt A remains readable but cannot become current under the new model hash. Legacy attempts predate attempt-local graphs, so the migration event now carries their prior boundary contract. This was the substantive defect found and fixed during the first review attempt.

3. Code walkthrough

A closed module contract

modules.js is the new center. It rejects unknown fields, invalid namespaces, non-exact identities, digest drift, unsafe repository-relative paths, provider executable injection, unknown trusted guards, invalid slots, duplicate IDs and gate keys, cross-slot edges, missing or disabled hard dependencies, and cycles.

skillmanualcommand are run descriptions. Observation is independent and names only an installed provider ID and version. This slice validates those descriptions; it does not yet execute them.

The model becomes data-driven

Workflow model v1.1.0 removes the new model’s hardcoded boundary.gates and scopeRouting. Ten built-in module definitions reproduce the old graph and stable CLI keys. The default policy enables all ten, leaving the behavior unchanged until a future project deliberately edits policy.

Projection preserves history

When a module-backed boundary begins, transitions.js embeds the resolved graph. projection.js validates that graph, derives gate order, and stores module ID/version/digest beside the familiar gate key. A model hash mismatch blocks the old attempt from review.

The middle branch is the remediation. It preserves a legacy attempt without rewriting the append-only journal or expanding the model lock into an archive of every historical model.

Discovery and local readiness remain separate

Discovery reads sorted regular JSON files under .gatereeve/modules/ and rejects symlinks. If .gatereeve/workflow.json is absent, only bundled defaults are selected: merely checking out a project manifest does not activate it. Readiness then reports missing skills or installed providers without changing the resolved definition or silently disabling a required module.

Tests and packaging

The new module contract suite exercises positive and adversarial graphs, policy-order independence, safe discovery, locked and configurable behavior, readiness, migration impact, and both module-backed and legacy replay. Canonical sources are staged into CLI packages and Desktop resources; inventory tests keep those consumers byte-aligned.

Boundary result: focused 16/16, CLI 208/208, Desktop 161/161, portable acceptance, packaging, document checks, and both dependency audits pass. UI, command execution, provider supervision, finalization passage, and GateReeve Release remain explicit later slices.
