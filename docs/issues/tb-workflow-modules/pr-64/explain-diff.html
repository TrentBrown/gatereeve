1 · Background

GateReeve separates lifecycle truth from observations

A governed feature is an append-only event journal interpreted through a pinned workflow model. Gate outcomes are not booleans scattered through the UI: each one is bound to an attempt, a model, declared inputs, dependency event IDs, and evidence. This is what lets GateReeve say that a result is current rather than merely successful at some point in the past.

Before this feature, the PR boundary already behaved like a dependency graph, but its checks were baked into the protocol. The preceding three slices made modules declarative, exposed them under the existing six-state rail, and added explicit manual, skill, command, and installed-provider adapters.

The crucial product decision is visible above: modules do not lengthen this rail. Selecting Implementing reveals a PR-boundary module graph; selecting Finalizing reveals the corresponding post-merge graph.

Definition: a provider reports normalized live progress and, when justified, a terminal observation. It cannot append workflow truth itself; only the protocol core can freshly validate and record passage.
2 · Intuition

Bind obligations to the thing they certify

Imagine a feature whose final PR produces merge commit abc…123. A release made from an older commit must not complete that feature, even if every release job is green. The finalization attempt therefore pins the merge, the active model, and the complete module graph.

Project with a release

An enabled required module holds the feature in Finalizing until its exact evidence passes or an allowed feature-scoped waiver is confirmed.

Project without a release

An empty finalization slot completes directly. GateReeve does not invent deployment ceremony for software—or other work—that has none.

3 · Code

Four layers cooperate without sharing authority

1. The model declares the graph

The default v1.2 model adds the feature.finalization slot and the built-in gatereeve/release definition. Resolution still validates IDs, versions, digests, dependencies, cycles, dispositions, and enabled policy.

{
  "slot": "feature.finalization",
  "id": "gatereeve/release",
  "observe": "gatereeve/release-conductor@1.0.0",
  "disposition": "required",
  "fingerprint": "feature-finalization-v1"
}

2. The generic core owns attempts and passage

finalization.js starts attempts, records outcomes or human waivers, invalidates changed evidence, and completes only through a fresh core transition. projection.js reconstructs eligibility and freshness from the journal. There is no release-specific feature state or transition.

3. Desktop renders and executes bounded actions

The renderer reuses the module card and details for Finalizing. Coordinator and IPC operations name a selected project, attempt, gate, and pinned module. Command modules use dedicated task PTYs; installed providers are supervised one-shot processes. Neither path borrows the persistent project shell.

4. The GateReeve provider adapts Release Conductor

The product-specific provider lives outside the generic core. Packaging bundles its import closure into a self-contained ESM entrypoint, hashes the executable bytes, unpacks only the installed provider, and runs it through Electron with ELECTRON_RUN_AS_NODE=1. The provider emits one bounded JSON response; the core decides whether that response may become an event.

4 · Independent review

Migration must preserve history and recovery

The first boundary attempt uncovered three related defects. Old feature-final records commonly called the merge field mergeCommitSha; interpreting those records through the new model could require the newer integrationSha retroactively. A model migration also made an active finalization attempt stale but left no way to replace it. Finally, mutation and replay disagreed about duplicate active attempts.

Old recordlegacy merge field
Retained snapshothistorical module graph
Preflight replaybefore durable writes
Old attemptsuperseded, retained
New attemptcurrent model + same merge

The remediation normalizes both field names to one full commit, rejects conflicting dual identities, evaluates merge and zero-module completion under the event's retained model, and projects every migration candidate before touching the marker, model lock, or journal. A different-model active attempt may be superseded; a second same-model attempt is rejected by both mutation and replay.

Result: the corrected source passes the full CLI, Desktop, portable-package, provider, migration, and exact-source CI suites. Independent re-review found no remaining blocker.
5 · After merge

The finalizing state now has a real job

PR #64 can prove the implementation and packaged runtime before merge, but it cannot prove that a public release contains its own future merge commit. After merge, GateReeve records that exact commit, starts the finalization attempt, and observes Release Conductor until its retained chain reaches terminal COMPLETE.

Still required: the signed installed-app walkthrough, direct and Homebrew installation, Apple Silicon and Intel-or-Rosetta launch/smoke evidence, public publication receipts, and the terminal conductor chain. These are pending obligations, not waived checks.
