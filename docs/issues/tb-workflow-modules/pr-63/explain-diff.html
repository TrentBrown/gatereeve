Background

GateReeve already understood a governed workflow as an append-only record. A boundary gate could be pending, passed, failed, or waived, and its result was meaningful only when bound to the exact model, attempt, dependencies, and evidence. The previous slice made those gates declarative modules and rendered them in the existing state-specific cards.

What it could not do was execute a module. A declaration could say that a step used a skill, a human attestation, or a command, but the Desktop had no safe adapter, no consent store, no dedicated process surface, and no way to ask an installed observer to interpret terminal evidence.

The architectural constraint
Execution is not passage. A process may run and a provider may describe it, but only the protocol core may append an authoritative gate outcome after rechecking freshness.

Intuition: a sequence of narrow hand-offs

The change treats module execution like a chain of custody. Each component receives only the authority it needs, and every boundary is explicit.

Consider a toy module that runs npm test. GateReeve displays the executable, argument array, working directory, effects, and unsandboxed authority. The user chooses Run once. The command gets its own named terminal—not keystrokes injected into the user's shell. Exit zero means PASS when no observer is required. A timeout or nonzero exit means FAIL. Clicking cancel records an attempt, but leaves the gate outcome unset.

Why a provider?

An exit code is sufficient for many commands. Some workflows need richer interpretation: a release conductor may complete in GitHub after the local process exits, or evidence may need exact source and checksum validation. An installed provider is a one-shot, out-of-process program. GateReeve sends one versioned JSON request on standard input and accepts exactly one matching JSON response on standard output.

{
  "requestId": "provider-123",
  "provider": {"id": "gatereeve/release-conductor", "version": "1.0.0"},
  "module": {"id": "gatereeve/release", "version": "1.0.0", "digest": "sha256:…"},
  "input": {"attemptId": "…", "inputFingerprint": "sha256:…", "evidence": {"taskId": "…"}}
}

The response must echo those identities. Stale fingerprints, duplicate lines, malformed JSON, crashes, missing executables, and timeouts all fail closed.

Code walkthrough

1. Canonical result and provider contracts

module-runtime.js is shared by the Plugin and Desktop. It defines the versioned request/response shape and command-result truth table. Structured command JSON is enrichment only: its allowed keys do not include an outcome.

2. Installed provider supervision

module-providers.js discovers application-owned manifests through an exact ID/version/digest allowlist. Manifests and executables must be regular, non-symlink files; relative executable paths must remain inside the installed provider directory. One-shot children use direct spawning with no shell, bounded output, a deadline, and shutdown cleanup.

3. Local command authorization

command-authorization.js stores private device-local grants. The grant fingerprint includes the Git common-directory identity, module version and digest, executable, argv, working directory, and observed entrypoint/support-file digests. Thus linked worktrees share a repository identity, different clones do not, and a detectable input change disables persistent authorization. The dialog explicitly says that this is not complete provenance or a sandbox.

4. Dedicated task terminals

module-task-manager.js creates named PTYs with project, module, attempt, and gate identity. It bounds retained output, supports input and resize, and terminates owned process groups with SIGHUP followed by SIGKILL. It preserves completed results for renderer reload while keeping the ordinary project shell separate.

5. Orchestration and fresh passage

module-execution.js retrieves the definition pinned by the selected boundary, checks eligibility, enforces consent, starts a task, writes private bounded evidence, optionally invokes a provider, and asks protocol-adapter.js to record only PASS or FAIL. The adapter first verifies that the pinned pull-request context is still current and reconstructs dependency fingerprints.

6. Narrow UI and IPC surfaces

The renderer gains command-consent and manual-attestation dialogs plus a session selector for the shell and named tasks. The preload and IPC contracts expose intent—module ID, consent choice, input, resize, cancel—not process configuration. Skill modules only provide copy/open-terminal assistance; GateReeve never launches an agent automatically.

What this guarantees—and what it does not

Guaranteed
  • No automatic command execution while opening or observing a project.
  • No renderer-selected executable, argv, cwd, provider path, or PID.
  • Exact provider and input identity before accepting an observation.
  • Fresh protocol-core validation before authoritative passage.
  • Separate project shell and task processes.
Intentionally not guaranteed
  • Commands are not sandboxed.
  • PATH tools, dependencies, credentials, and network effects are not fully provenance-checked.
  • No concrete release provider ships in this slice.
  • Feature-finalization passage arrives in the next slice.
