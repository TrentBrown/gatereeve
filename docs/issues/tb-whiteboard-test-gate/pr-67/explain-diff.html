Background

What GateReeve already did—and what was missing

GateReeve governs a feature through an append-only protocol record. At a PR boundary, named gates evaluate one pinned base/head range. The protocol core—the reeve—decides eligibility, verifies freshness, and records outcomes. A skill, model, UI, or shell command cannot grant passage by itself.

Before

Judge

Judge expressed a compliance decision, but its execution did not yet have a reusable, runtime-enforced guarantee of a fresh context with no inherited implementation history.

Missing

Whiteboard Defense

There was no independent artifact that asked adversarial open-ended questions, then let a colleague reveal concise, deep, evidence-backed, and “Push Harder” answers.

Constraint

Portable plugins

The behavior must work under Codex and Claude Code, through the headless CLI and Desktop, without welding either gate into the core product.

Key distinction: Judge answers “does the work satisfy the approved contract?” Whiteboard answers “did we produce a defensible explanation of exactly this change?” Whiteboard never certifies that a human understands the code.
Intuition

Think of the runtime as a clean-room review conveyor

Each agent stage receives a sealed snapshot and a typed assignment. It returns typed output plus a receipt. Only trusted host code validates and publishes the declared artifacts; only the protocol core records the gate result.

1. PinExact base/head and gate inputs
2. SnapshotRead-only commit plus digest-bound sidecars
3. IsolateFresh Codex or Claude context
4. ValidateSchema, receipts, HTML runtime, evaluator
5. RecordRecheck freshness, then append outcome

Toy example

Suppose a PR moves route selection into a central router. Challenger asks: “Why does routing belong here?” Defender answers at three depths and cites src/router.js:10-22. If the implementation has poor rejection metrics, the artifact highlights that limitation but may still pass. If the HTML omits the evidence reveal or loads helper.js, the artifact itself is defective and must fail.

Architecture

Shared mechanics, separate responsibilities

Judge lane

  1. Waits for Verification.
  2. Runs one independent compliance-review context.
  3. Receives spec, rubric, pinned change, and Verification evidence.
  4. Publishes bound JSON, Markdown, and receipt.
  5. FAIL blocks. It never edits code.

Whiteboard lane

  1. Depends on Verification and conditionally waits for Judge.
  2. Runs isolated Challenger, then isolated Defender/Publisher.
  3. Preserves every question verbatim.
  4. Publishes a challenge-and-reveal HTML study artifact.
  5. Work findings do not block; artifact defects do.

The after edge is only an ordering/freshness edge. Whiteboard receives no Judge output. Content flows only through explicit dependsOn edges, which prevents the explanation from simply echoing the Judge.

Code walkthrough

Four changes make the design real

1. A reusable staged-agent primitive

Module definitions now declare stages, provider-neutral capability requirements, resources, output schemas, isolation policy, artifact allowlists, and one authoritative evidence root. The runtime checks the provider descriptor before launch and binds each result to its request.

module.run = {
  kind: "agent-workflow",
  capabilityProfile: { id: "high-capability-v1", minimumReasoning: "high" },
  isolation: { freshContext: true, inheritedTurns: 0 },
  repositoryAccess: "read-only-pinned",
  networkAccess: "denied",
  stages: [/* typed, ordered stages */]
}

2. Actual isolation in both providers

Codex uses an ephemeral execution against GateReeve’s disposable snapshot. Claude Code uses a non-persistent restricted custom agent. Receipts record requested capability, actual provider/model/reasoning, opaque context ID, zero inherited turns, timestamps, policies, and digests. A reused context or mismatched capability leaves the gate UNSET.

3. A genuinely independent Whiteboard plugin

The marketplace registry composes Agentic Development Workflow and Whiteboard Test into separate Codex and Claude packages. Installing Whiteboard does not activate it; policy selection and any in-flight model migration remain explicit.

4. Free-form presentation with governed artifact validation

The model retains freedom to author embedded HTML, CSS, JavaScript, SVG, animation, and diagrams. The host then parses and executes the exact generated bytes in a restricted DOM, rejects non-embedded resources, checks runtime errors, exercises native reveals, verifies visual alternatives and finding links, and binds that receipt into whiteboard-defense.json. Desktop adds a sandboxed, no-authority CSP when displaying it.

Failure model

Three outcomes that must not be confused

Judge FAIL

The work is noncompliant. The gate blocks. A separate implementation context repairs it, then a new pinned Judge attempt reviews again.

Whiteboard FAIL

The explanatory artifact is malformed, unsupported, incomplete, or mechanically broken. This says nothing by itself about implementation quality.

Whiteboard PASS + finding

The artifact honestly exposes an implementation limitation or unknown. That disclosure is successful explanatory behavior, not a reason to pretend the weakness does not exist.
