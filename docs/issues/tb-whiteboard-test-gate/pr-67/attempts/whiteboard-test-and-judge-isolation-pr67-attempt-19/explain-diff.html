1. Background: explanation is not validation

Whiteboard teaches

It asks open-ended questions, lets a reader pause, then reveals concise and deep defenses, exact evidence, visual models, and “Push Harder” follow-ups. It highlights weaknesses without grading the work.

Judge validates

It independently checks the pinned implementation against the approved specification and rubric. A FAIL blocks the boundary. It never edits code or consumes Whiteboard output.

These responsibilities deliberately overlap in subject matter but not authority. A persuasive explanation cannot turn broken code into acceptable code, while a correct implementation can still be explained poorly.

2. Intuition: a governed oral exam

Think of Whiteboard as a self-guided oral exam prepared by two strangers to the implementation thread. The Challenger decides what an engineer should be able to defend. A separate Defender/Publisher answers every unchanged question from pinned repository evidence and packages the result as a self-contained interactive page.

A Whiteboard PASS means: the explanation artifact is complete, substantive, evidence-backed, internally consistent, and operable. It does not certify the implementation and it does not claim a human reader understands it.

3. Architecture: shared mechanics, separate minds

Each stage receives an immutable read-only Git snapshot, denied network access, disposable scratch space, typed schemas, a high-capability provider profile, and a receipt binding context identity, provider settings, instructions, input, output, and snapshot. The protocol core rechecks freshness before it accepts the evaluator's result.

5. Evidence: retries remain history, not clutter

Every attempt gets its own immutable directory. Boundary manifest schema v2 names the exact current artifact path and SHA-256 digest, so a preserved earlier failure can never masquerade as the current pass and a later retry never overwrites old evidence.

6. Check your model

Why is Whiteboard ordered after Judge but not dependent on Judge evidence?

Ordering avoids simultaneous expensive work and lets Judge finish first when present. Keeping Judge out of Whiteboard's evidence dependencies prevents bias and lets Whiteboard run when Judge is disabled.

What is the most important difference between a work weakness and an artifact deficiency?

A work weakness belongs in a visible finding and does not make Whiteboard fail. An artifact deficiency—missing evidence, broken interaction, omitted question, false attestation, or invalid provenance—means GateReeve did not produce a defensible explanation and therefore does fail Whiteboard.

Why are both schema validation and DOM execution necessary?

Schemas prove the structured claims are complete and typed. Executing the actual HTML proves those claims survive publication: controls operate, findings are visibly located and linked, scripts do not fail, visuals are accessible, and forbidden authority is absent.

Why does the manifest derive substantive status from the Defender?

The host may validate structure and behavior, but it cannot honestly invent the model's claim that the explanation is deep and defensible. Requiring and binding the attestation makes that responsibility explicit and auditable.

Why preserve every failed attempt?

Failures explain how the contract was hardened and provide immutable evidence for the event that referenced them. Current passage is selected by an exact path-and-digest manifest, not by deleting history or overwriting a mutable “latest” file.
