1. Why this exists

Whiteboard teaches

It poses open-ended challenges, lets the reader pause, and reveals a layered defense with evidence and “Push Harder” follow-ups. It reports work weaknesses honestly but does not grade the implementation.

Judge validates

It independently checks the pinned implementation against the approved spec and rubric. A failing verdict blocks the boundary. It does not repair its own findings.

The separation matters because an explanation can be excellent while the implementation is wrong, and a correct implementation can be explained poorly. One artifact should never smuggle the authority of the other.

2. System shape

Every model stage receives a read-only snapshot of exact Git objects, denied network access, a disposable scratch area, typed input/output schemas, and a receipt that binds requested capability, actual provider settings, instructions, input, output, and snapshot.

3. The Whiteboard contract

The plugin is independently packaged and disabled by default. When selected, it depends on Verification and is merely ordered after Judge if Judge is enabled. The Judge artifact is never supplied as Whiteboard content.

4. The Judge contract

Judge v2 runs once in a fresh, read-only context. It receives the spec, rubric, exact pinned change, and a digest-verified Verification snapshot. It performs criterion, scope-creep, gap, and contradiction checks. PASS or FAIL is recorded exactly as returned; there is no self-correction loop.

5. Evidence must outlive the attempt

Early boundary runs wrote some reports at fixed packet-root names. That was unsafe for retries: a preserved failure could be mistaken for the current pass, or a current report could overwrite bytes referenced by an older event.

The final design uses two complementary rules:

  1. Every formal gate can resolve its output under attempts/<attempt-id>/.
  2. Boundary manifest schema v2 names the exact current report path and SHA-256 digest.

Historical attempt directories and known legacy root reports remain auditable. Symlinks, unsafe attempt IDs, digest drift, and unrelated packet files are rejected. “Latest” is a manifest decision, not a mutable filename.

6. Review yourself

Why is Whiteboard ordered after Judge but not dependent on Judge evidence?

Ordering avoids simultaneous expensive work and lets Judge finish first when enabled. Keeping Judge out of dependsOn prevents its conclusions from biasing Whiteboard content and lets Whiteboard run when Judge is disabled.

What does a Whiteboard PASS actually claim?

Only that GateReeve produced a complete, defensible, evidence-backed explanatory artifact whose required interactions and containment checks pass. It does not certify the implementation or a reader’s understanding.

Why are two Whiteboard contexts needed?

The Challenger must pose genuinely adversarial questions without sharing the Defender’s hidden reasoning. The Defender/Publisher receives only typed challenge output and pinned evidence, then must preserve every question in the final artifact.

Why execute generated HTML instead of scanning strings?

Static markers cannot prove scripts load, controls work, links resolve, or relative resources are absent. Bounded DOM execution tests the actual bytes that will be published while retaining freeform presentation.

Why bind report paths and digests in boundary schema v2?

A PR can have many attempts. Explicit path-and-digest references identify the exact evidence that granted current passage without deleting or overwriting earlier failures.
