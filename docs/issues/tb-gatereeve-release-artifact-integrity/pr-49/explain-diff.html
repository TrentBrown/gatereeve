Background

The beginner's view: a release is a chain of custody

A macOS release is not trustworthy merely because its last file has a valid signature. The system must also prove where that file came from, whether anything disappeared during transport, which source revision produced it, which notarization request covered it, and whether publication used exactly those retained bytes.

Prepare complete Plugin tree
Round-trip and verify
Sign, notarize, staple
Publish sealed bytes
Install and assess

The bug behind this feature lived early in that chain: a hosted artifact transfer could omit intentionally hidden Plugin files. A later stage could then see a plausible but incomplete tree. The correction gives the producer a complete file commitment and makes every consumer verify it.

Intuition

Think of the producer manifest as a tamper-evident packing list. If the producer packed four files, the consumer may not accept three matching files, four files with one changed byte, or five files with an unlisted addition. Exactness works in both directions.

Producer commitment
  .claude-plugin/plugin.json   size=812   sha256=…
  .codex-plugin/plugin.json    size=760   sha256=…
  RELEASE.json                 size=436   sha256=…
  shared/commands/...          size=…     sha256=…
  aggregate tree digest                  sha256=…

Consumer rule
  observed paths + sizes + bytes == producer commitment
  AND marketplace semantics are valid

The second half matters. A perfectly preserved but semantically incomplete Plugin is still invalid. GateReeve therefore requires both exact-byte agreement and product-level validation.

Why the release uses several protected runs

Each run represents a different authority or recovery boundary. Apple credentials create trusted bytes in release-trust. Read-only finalization seals a plan. A nonpublishing rehearsal proves that the plan can be consumed without mutation. Only then may release-publication use publication authority. If a later surface fails, a fresh dispatch resumes from the same retained packet; it does not rebuild or silently replace history.

Core invariant: once Apple trust production creates live bytes or a notarization request, recovery may continue only with those exact bytes and the recorded request history.
