GateReeve release engineering · PR #47

Trust the run for execution; trust the packet for release identity

This explanation covers exactly 9a00ec8..e263097. The change repairs linked Homebrew Cask finalization after a valid recovery publication ran from a newer main commit than the immutable notarized release source.

Background

A GateReeve release deliberately separates authority. Preparation creates and notarizes immutable bytes. Finalization seals a publication plan. Primary publication creates the tag, GitHub prerelease, marketplace update, and update metadata. Only after the public DMG has been installed and launched does a separately approved workflow publish the Homebrew Cask.

RC.6 exposed a legitimate divergence. Its notarized source was 10a7264, while a bounded recovery publication was dispatched from a later main head, cf9bbf7. The old Cask check required those SHAs to be equal. That condition confused the code used to execute a recovery with the older bytes the recovery was authorized to publish.

Invariant: a newer reviewed main may publish an older sealed source, but an arbitrary branch may not produce release authority, and the downloaded packet must still name the exact requested source and tag.

Intuition

Think of a bank transfer. The bank software version that processes the transfer and the account statement identifying the transfer are different evidence. We require the software to be an approved production version; we require the statement to identify the exact transaction. Requiring the software revision to equal the transaction’s creation revision is unnecessary and breaks legitimate recovery.

Toy example

immutable release source: A
reviewed main later:      A—B—C
workflow dispatch head:      C
sealed packet:           { source: A, tag: rc.8 }

Accept when:
  producer branch == main
  A is an ancestor of C
  packet.source == A
  packet.tag == rc.8

The ancestry check permits reviewed fixes after the release source while preventing unrelated histories. The packet comparison prevents a successful run from being reused for a different release.

Code walkthrough

1. Finalization verifies two independent identities

homebrew-cask-finalize.yml now requires the upstream primary publication to be a successful dispatch of the expected workflow from main. It extracts that run’s head and proves the requested immutable source is its ancestor. After downloading the retained result, it independently checks the record’s source commit and tag before sealing a Cask plan.

run.head_branch === "main"
git merge-base --is-ancestor "$SOURCE_COMMIT" "$primary_run_head"
record.source.commit === SOURCE_COMMIT
record.source.tag === TAG

2. Rehearsal and publication apply the same rule

Both jobs in homebrew-cask-publish.yml use the same layered check for the Cask-finalization producer and its downloaded packet. The read-only rehearsal remains unable to mutate distribution. The protected publication job still requires its separate plan digest, approver, environment, and publication token.

3. Contract tests prevent regression

coordinated-workflow.test.js asserts that all three paths reject the obsolete head-equality rule, require main, require ancestry, and compare packet source/tag inputs. This makes the distinction visible in review and resistant to accidental simplification.

4. Workflow records explain the operational discovery

The cumulative feature record captures the successful direct RC.6 installation, the failed preflight assumption, the corrective slice, and the permanent decision. No Cask publication occurs in this PR.

Residual boundary: GitHub metadata establishes reviewed producer provenance; the current checked-out CLI validates the packet. Neither check replaces the protected publication approval.
