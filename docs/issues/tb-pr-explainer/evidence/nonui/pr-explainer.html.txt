<header><div class="eyebrow">GateReeve · PR 101 · pinned engineering walkthrough</div><h1>Publish complete markers before other writers can read them</h1>
<p class="lead">Several processes can start collecting workflow measurements at once. This slice changes how a new metrics directory becomes recognizable as an owned store, so another process cannot read an empty, partially published ownership marker.</p>
<p>It also makes readers tolerate the brief extra hard link created by publication. The scope is exactly two mirrored <code>performance/store.js</code> files: 58 insertions and 16 deletions in total. No tests, database schema, report UI, or retention rules change in this comparison.</p>
<p class="small">Intent: <a href="https://github.com/TrentBrown/gatereeve/pull/101">PR #101</a>, “fix: publish metrics store marker atomically for concurrent first writers.” Caller feature identity: <code>tb-metrics-sqlite-store</code>. This page covers only the atomic marker publication slice.</p></header>

<section id="context"><h2>The admission check comes before SQLite</h2>
<p>The measurement subsystem records observations such as operation durations and outcomes. Its local directory contains an <strong>owner marker</strong> with the exact text <code>gatereeve-performance/1\n</code>, a private <strong>key</strong> used to derive HMAC identities, and a SQLite database. “Owned” means the directory passes the store’s admission checks; the marker prevents casually adopting an unrelated nonempty directory. <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/PERFORMANCE.md#L40-L46">Storage and interpretation contract</a></p>
<div class="card"><p><strong>Write path:</strong> <code>record()</code> → <code>put()</code> → open database → <code>admit(true)</code> → read/create owner marker → initialize SQLite → read/create key → normalize identities → transaction.</p>
<p class="small">The marker race happens before SQLite’s write-lock waiting can help. On a collection error, <code>record()</code> warns and returns null while underlying work continues; observations can be missing even when the work succeeds. <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/performance/observe.js#L8-L14">Collector failure behavior</a> · <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/performance/store.js#L350-L368">Store write path</a> · <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/performance/store.js#L153-L175">Database admission and initialization</a></p></div></section>

<section id="mechanism"><h2>Three cooperating changes</h2><div class="grid"><div><h3>1. Publish with a no-replacement operation</h3><p>The temporary file is created exclusively with mode <code>0600</code>. Only after its write completes does <code>link()</code> introduce the final name. An existing <code>owner</code> wins. The catch path accepts that winner only if its published marker is valid, and the <code>finally</code> block attempts to remove this process’s temporary name.</p><p>The directory may contain other names matching <code>.owner-</code> plus 36 lowercase hex-or-hyphen characters during adoption. Other names still trigger the nonempty-directory refusal, unless a valid owner appeared concurrently. The allowlist checks names, not file contents or their creators.</p></div><div><pre tabindex="0"><code>127        const pending = join(this.root, `.owner-${randomUUID()}`);
128        try {
129          check((await readdir(this.root)).every(name =&gt; PENDING_OWNER.test(name)), &#x27;Refusing to adopt a nonempty directory&#x27;);
130          await writeFile(pending, MARKER, { flag: &#x27;wx&#x27;, mode: 0o600 });
131          await link(pending, join(this.root, &#x27;owner&#x27;));
132        } catch (error) {
133          // A concurrent first writer may have adopted the directory meanwhile.
134          if (await publishedFile(join(this.root, &#x27;owner&#x27;)).catch(() =&gt; null) === MARKER) return;
135          throw error;
136        } finally { await unlink(pending).catch(() =&gt; {}); }</code></pre><p class="ref"><a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/performance/store.js#L127-L136">Source · head · lines 127–136</a></p></div></div>
<div class="grid"><div><h3>2. Wait through the hard-link handoff</h3><p>A hard link is a second directory name for the same file. Between <code>link()</code> and <code>unlink()</code>, <code>owner</code> can therefore have two links. The unchanged strict reader requires a regular file, a single link and at most 8 KiB, and opens with <code>O_NOFOLLOW</code>.</p><p>The new wrapper first tries that strict reader. On “Unsafe metrics file,” it checks the current link count and retries only for counts one or two. It permits up to 50 delays of 10 ms: about 500 ms of requested waiting, plus I/O and scheduling time. Success still requires the strict check to pass. Missing paths, other errors, counts outside that range, and exhaustion are thrown.</p><p class="small">A count of one can still merit retry: the temporary name might have been removed between the failed handle check and the subsequent pathname check. That rationale is recorded in the source comment. <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/performance/store.js#L20-L37">Strict reader and publication wrapper</a></p></div><div><pre tabindex="0"><code> 28  async function publishedFile(path) {

<h3>3. Apply the same reader to owner and key</h3><p>The key already used temporary-file-plus-link publication in the base. This slice routes its initial read, post-creation read, and uncached <code>identity()</code> read through <code>publishedFile()</code> too. It preserves the winner’s key, which is used to hash private identifiers. Cached key reads remain cached. <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/performance/store.js#L232-L248">All key-reader changes</a></p>

<section id="attention"><h2>Where a reviewer should look closely</h2><ol>
<li><strong>Publication safety versus recovery.</strong> The final name never replaces a concurrent winner. However, if a publisher exits after linking and before unlinking, the extra link can remain. The reader eventually refuses it; this patch adds no stale-link recovery. Examine whether that bounded refusal matches the intended operational policy. <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/performance/store.js#L24-L37">Retry policy</a> · <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/performance/store.js#L127-L136">Temporary cleanup</a></li>
<li><strong>Directory adoption boundary.</strong> Concurrent pending owner names are now tolerated before ownership exists. The pattern validates the spelling of names only. A nonmatching entry remains disallowed, and a valid concurrent marker may win the catch path. Check that this narrow widening matches the store’s ownership contract. <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/performance/store.js#L9">Allowed pending names</a> · <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/plugin-src/shared/resources/performance/store.js#L120-L136">Admission logic</a></li>
<li><strong>Evidence coverage of timing boundaries.</strong> The unchanged test and retained CI support concurrent first writes, but do not separately demonstrate retry exhaustion, a permanently extra-linked file, or an interruption at each publication step. The source preserves strict acceptance checks; those cases are review questions rather than newly demonstrated runtime results. <a href="https://github.com/TrentBrown/gatereeve/blob/aa9541fe824da53a82f13b09a5fa566cfc65aa9a/cli/test/performance.test.js#L81-L87">Test scope</a></li>
</ol><p>These are specific paths and tradeoffs to inspect. This artifact supplies no review verdict, merge recommendation or GateReeve passage.</p></section>
