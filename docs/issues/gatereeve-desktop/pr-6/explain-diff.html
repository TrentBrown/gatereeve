Background

The broad picture: observation, not orchestration

GateReeve governs software work through an append-only event journal and a pinned state-machine model. The plugin can enforce transitions; the Commander CLI exposes the same protocol as a control and inspection surface. GateReeve Desktop has a narrower promise: it lets a person understand one selected feature record without becoming another workflow engine.

The first three Desktop slices established that architecture, built the Electron shell and observation lifecycle, and rendered the state-first experience. This fourth slice closes two deliberately deferred concerns: drawing human attention at the right time and proving that the application is both accessible and genuinely runnable on its supported systems.

The narrow problem: a refresh is not an event

The Desktop recomputes a complete observation whenever local records change, the window regains focus, the user refreshes, or GitHub polling discovers new evidence. If every refresh that contained a failed gate generated a notification, the application would punish the user for looking at it. Conversely, if it compared only the latest GitHub response, it might miss a merge already recorded in the journal or report it twice.

Key distinctionA notification represents entry into an attention-worthy condition. Re-reading an unchanged condition is silent.

Intuition

Take a quiet photograph, then compare

Imagine opening a worktree whose verification gate is already failing. The app takes that observation as its baseline and says nothing. Later the gate passes; later still it fails again. Only the re-entry into failure produces a notification.

Enabling notifications works the same way. Opting in does not replay everything already visible on screen. It establishes a fresh baseline and waits for something new.

Two kinds of memory

Active conditions

Failure, staleness, inconsistency, suspension, and ready human-confirmation actions can clear and re-enter. Their keys live in the current observation map.

One-shot events

Review requests, merges, and completion should not replay if a source disappears temporarily. Their identities remain in a process-lifetime observed set.

One PR identity

A merge seen through GitHub and a merge recorded in the journal both use merge:pr:12. Whichever arrives first suppresses the duplicate.

Freedom stays outside the trust boundary

The renderer can ask for one thing: set a boolean notification preference. It cannot construct a native notification, advance a workflow transition, run a command, or choose an arbitrary file. Main process code compares canonical observations and invokes Electron's native notification API.

Code walkthrough

1. Candidate extraction and transition comparison

main/notification-observer.js converts a snapshot and optional pull request into a map of stable candidate keys. It keeps presentation text beside each key, while the comparison algorithm deals only in identity.

reset(snapshot, pullRequest) {
  active = notificationCandidates(snapshot, pullRequest)
  observedEvents = oneShotKeys(active)
}

observe(nextSnapshot, pullRequest) {
  for (const candidate of notificationCandidates(...)) {
    if (!active.has(candidate.key) && !observedEvents.has(candidate.key)) {
      notify(candidate)
    }
  }
}

Notification delivery is wrapped so an OS-level failure cannot turn a valid workflow observation into a Desktop error.

2. Coordinator lifecycle

main/coordinator.js now holds the observer beside its watcher and poller. Opening a worktree and changing the opt-in preference reset the baseline. Fully enriched local refreshes and GitHub polling compare observations. Closing the coordinator still owns all teardown.

Only now compare the complete observation with the prior baseline.

3. A narrow, accessible preference surface

The shared contracts, IPC handler, preload bridge, and renderer each admit the same boolean. The sidebar presents a native checkbox with visible explanatory text, and renderer tests prove state round-trips through the preference control.

The accessibility pass also labels the attempt selector explicitly, extends focus treatment to inputs and the trusted HTML frame, keeps status understandable without color, and removes a forced minimum width that could create horizontal overflow at the documented 760×560 window size.

4. Runtime proof that preserves sandboxing

The CI workflow adds three runtime jobs: Ubuntu 22.04, Ubuntu 24.04, and macOS 14. Each installs only the Desktop package and launches its smoke mode. Ubuntu's runners need Electron's Chromium SUID helper to be materialized and configured before launch.

node apps/desktop/node_modules/electron/install.js
sudo chown root:root apps/desktop/node_modules/electron/dist/chrome-sandbox
sudo chmod 4755 apps/desktop/node_modules/electron/dist/chrome-sandbox
xvfb-run --auto-servernum npm start --prefix apps/desktop
Why this mattersThe implementation did not make CI green by adding --no-sandbox. The proof exercises the secure application configuration users receive.
