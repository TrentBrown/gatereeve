Background

GateReeve is a protocol enforcer, not a task runner. Agents remain free to reason and implement, but meaningful workflow passages—design approval, plan authorization, PR review, and the like—are recorded as events and accepted only when their guards hold.

From events to a current state

The durable truth is an append-only journal. A projection folds those events into the current feature, slice, boundary attempt, gates, decisions, and blockers. That separation matters: history answers “what happened?”, while the projection answers “where are we now?”

events.jsonlImmutable passages and gate outcomes
→
Protocol projectionCurrent state derived from history
→
Observer surfacesPlugin, CLI, and future Desktop

Before this PR, GateReeve already had observer operations such as status, next, history, and graph. They were useful to people and agents, but they did not form the compact, versioned, deeply validated contract that a long-lived graphical client needs.

The architectural boundary Desktop will consume the same shared protocol used by the plugin and CLI. It will not reconstruct governance independently. If the state machine changes, one canonical implementation changes with it.

Why a desktop client needs two shapes

Snapshot

A compact overview: current feature and slice, milestones, gate graph, artifacts, source freshness, blockers, and possible actions.

Named detail

A focused read for one artifact, the complete event stream, one attempt, or the pinned workflow model.

Protocol envelope

A stable success/error wrapper shared across direct plugin calls and Commander commands.

Fetching everything on every refresh would waste work and couple overview rendering to large artifacts. Fetching too little would force Desktop to infer semantics. The snapshot/detail split keeps the overview cheap while preserving exact drill-down.

Intuition

Think of the snapshot as a train-station departure board. It tells you what exists, what is current, and what can happen next. Named reads are the ticket desk: they retrieve one identified item, but they do not let callers wander through the station’s filing cabinets.

Readiness is more than eligibility

An action may be structurally allowed by the state machine but still need evidence or freshly inferred facts. The new contract therefore distinguishes three states:

availableThe action belongs at this point, but prerequisites are not yet fully known.
readyThe action is structurally eligible and every required prerequisite passes.
blockedThe state machine disallows it, or a known prerequisite fails.

For example, “request human review” might be structurally eligible after explain-diff, but remain merely available until packet validation is known. Once validation passes it becomes ready. If code review fails, it becomes blocked and explains why.

{
  "id": "request-review",
  "authority": "agent",
  "readiness": "available",
  "inputs": [{ "id": "fingerprintsFile", "required": true }],
  "prerequisites": [{ "id": "packetValidation", "status": "unknown" }],
  "reasons": ["Packet validation has not been recorded"]
}

An inventory, not a filesystem browser

The snapshot emits stable artifact IDs such as spec, tracker, and attempt-3:judge. A caller can request an artifact by one of those IDs. It cannot submit a path. At read time, GateReeve resolves the inventory entry again, checks lexical containment, resolves symbolic links, checks real-path containment, enforces a 10 MiB ceiling, and then returns format-aware content.

Artifact IDMust exist in canonical inventory
→
Containment checksLexical path and resolved real path
→
Typed resultMarkdown, JSON, JSONL, HTML, or text

If a symlink points outside the feature directory, it is already marked unsafe and unavailable in the inventory. The detail read repeats the check, closing the gap between observation and use.

Raw HTML is intentional Explain-diff HTML is returned unchanged. This project has only the user and their agents as actors, and the product decision is to preserve the artifact exactly. Any presentation policy belongs to the future Desktop renderer, not this protocol slice.

Version provenance prevents plausible lies

The snapshot separately reports the model pinned by the feature, the model bundled with the running software, the supported catalog, and any migration impact. A future client can diagnose older records without pretending that an incompatible model is actionable.

Code walkthrough

The implementation is deliberately layered. The largest file defines meaning and validation once; the adapter and Commander surfaces remain thin transports.

1. Canonical snapshot and detail contracts

plugin-src/shared/resources/protocol/snapshot.js adds schema version 1 for both result types. It builds artifact and milestone catalogs, derives source status and readiness, supplies exact command templates, reports model provenance, performs named reads, and validates every nested structure.

export const SNAPSHOT_SCHEMA_VERSION = 1;
export const DETAIL_SCHEMA_VERSION = 1;

const DETAIL_KINDS = new Set([
  'artifact', 'events', 'attempt', 'model'
]);

export function validateSnapshot(snapshot) { /* deep contract checks */ }
export function validateDetail(detail) { /* kind-specific checks */ }

Deep validation is important here. Checking only top-level fields would permit values such as events: null, malformed model graphs, or artifact payloads whose declared format disagrees with their data. Boundary attempt 1 found that weakness; the remediation added direct negative tests for each nested family.

2. Existing observer, plugin, and CLI surfaces converge

The shared observer gains snapshot and read operations. The plugin adapter exposes them directly. Commander.js adds matching commands while retaining all existing operations and human-oriented output.

SurfaceOperationRole

This realizes a key product decision: state-machine governance is baked into the GateReeve plugin; the CLI is an optional surface over the same behavior, not a dependency of the plugin.

3. Exact protocol staging

The CLI distribution stages the canonical shared protocol rather than maintaining a handwritten copy. The staging utility recursively inventories files, hashes their bytes, and writes a deterministic manifest. Builds for both native package targets must agree.

{
  "schemaVersion": 1,
  "canonicalSource": "plugin-src/shared/resources/protocol",
  "protocolHash": "sha256:1e71e3b…",
  "files": [{ "path": "snapshot.js", "size": 41234, "sha256": "…" }]
}

The exact file size above is illustrative; the verified protocol hash is real. The important property is that added, missing, or modified staged files alter the manifest and are caught by validation.

4. Tests follow the risks

The new test suites do more than snapshot happy-path JSON. They check diagnostic modes, source independence, readiness transitions, plugin/CLI parity, absence of journal mutation, structured JSONL reads, unchanged HTML, size and path rejection, deterministic manifests, malformed nested contracts, and escaping symlinks.

5. Documentation and lifecycle artifacts

README and user guides document the new observer commands. The feature folder captures the approved design, specification, implementation plan, slice ledger, rubric tracker, decision history, and formal PR evidence. Those files account for much of the diff because this branch establishes the lifecycle for the broader Desktop feature, while product code in this PR remains limited to the first protocol slice.
