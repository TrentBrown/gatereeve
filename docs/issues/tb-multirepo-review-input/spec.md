# Spec - tb-multirepo-review-input

**Feature:** `tb-multirepo-review-input`
**Created:** 2026-10-23
**Status:** validated for planning (2026-10-23)
**Design:** [design.md](design.md), approved by `evt-model-led-design-approved-20261023`
**Supporting input:** [interview.md](interview.md), D1-D10

## Summary

Replace prescribed execution choreography with model-led orchestration inside
explicitly authorized phases. Keep the planning backbone and required gates,
with current evidence and authority enforced at milestones. Retain local shared
requirements and evidence independently of application Git. Cut over directly,
with a current-protocol resume entry rather than backward compatibility.

The requirements below specify the resulting software, not permission to merge,
publish, install or deploy it. Historical interview proposals superseded by
D6-D10 do not add requirements.

## Definition of Done

The global software-development Definition of Done applies to implementation.
This specification's validation is not evidence that its product criteria pass.

## Acceptance Criteria

- **AC1.** A feature retains interview, approved design, validated spec, plan and issues; the model can choose and revise work/check order within an authorized phase, declare readiness without launching review, and remediate without a fixed round limit. The system blocks milestone passage when applicable gate evidence or human authority is missing, failed without an authorized exception, or stale, and identifies the missing obligations.
- **AC2.** A feature in a single repository or a parent folder above nested repositories can prepare review and finalize evidence without tracking or committing its documents in application Git. Review uses exact approved requirement bytes and independently pinned application source; unsafe paths, altered/missing evidence, cross-feature references and interrupted publication cannot become accepted current proof.
- **AC3.** Every required gate retains its own verdict and evidence. One fresh evaluator independent of the implementer can supply separate code-review and spec-acceptance verdicts in one execution; unsupported evaluator roles, absent verdicts and fabricated execution receipts cannot satisfy obligations.
- **AC4.** Intact qualifying results are reused when their relevant inputs remain equivalent. Changed or uncertain inputs require appropriate refreshed evidence; an independent delta assessment may supplement prior review only with explicit coverage of the change and its interactions. Final acceptance covers the current candidate, with original result provenance preserved.
- **AC5.** Independent reviewers receive bounded prior findings, coverage limits and clearly identified disposition claims, verify affected resolutions, and can report new supported defects under approved gate criteria. Unaffected findings need no repetitive reconciliation; raw implementation conversation and unrelated advice cannot silently determine acceptance.
- **AC6.** One explicit, scoped human decision can authorize named quality exceptions or requirement amendments and any expressly named continuation actions. The system records actual available provenance, preserves failures and old requirements, refreshes affected proof, displays exceptions, and never infers merge authority or fabricates a passed check or actual integration.
- **AC7.** Protected milestone adapters and supported host hooks consult the same core, revalidate the action/candidate, and block unavailable or invalid passage while allowing corrective work. CLI, native plugins and desktop show consistent current obligations, evidence, exceptions and enforcement coverage, with incidental ordering controls removed and routine records generated by operations.
- **AC8.** The distributed implementation uses one current protocol without a legacy execution/replay path, automatic state migration, staged opt-in pilot or benchmark prerequisite. Resuming older work preserves its files, establishes current commitments and authority without restarting unchanged planning, and refreshes proof that cannot satisfy current contracts. Existing receipts support practical observation and iteration on real projects without an added evaluation gate.

## Contract details

### C1. Milestones, obligations and model freedom (AC1, AC3, AC7)

| Boundary | Required state and proof |
| --- | --- |
| Begin implementation | Current approved design, validated spec, plan/issues and applicable human implementation authorization |
| Enter human acceptance | All applicable required validations and review evidence current, or explicitly accepted exceptions under gate policy; current review packet |
| Merge | Applicable acceptance, explicit action/candidate authorization (direct or derived from an applicable standing grant), source/PR synchronization and protected merge checks |
| Declare completion | Actual integration evidence, complete-feature coverage, required finalization and local-retention status; visible accepted exceptions where policy permits |

These boundaries do not gate each edit or commit. A failed validation cannot
prevent repair in an already authorized phase. Model freedom cannot disable
required gates, expand commitments, self-certify an independent role, change
exception policy or infer approval. Remediation has no count-based halt;
explicit project stop decisions remain applicable.

Replace cross-gate `dependsOn`, `before`/`after` and owner ordering as scheduling
controls with typed required inputs where evidence truly must exist. No new
universal review sequence replaces the graph. Internal steps necessary to
produce a particular validator's proof are allowed; this is not permission to
remove real causal requirements inside a validator.

Preserve the obligations represented by the currently enabled default modules:
source/context pinning, record reconciliation, Verification, spec evaluation,
pattern review, independent Judge, code review, decision triage, explain-diff,
packet validation and required finalization/release obligations. Optional
whiteboard assessment remains policy-controlled. Bookkeeping can be generated
without separate agent turns. No substantive gate is silently deleted, disabled
or converted into a presentation-only item. Release actions still need their
own authorization; this feature does not redesign publishing or trust policy.

Grouping code/spec assessment changes session count, not verdict count or
criteria. Existing additional Judge obligations remain explicit; D6 does not
silently authorize removing them. Each gate retains its declared evaluator role.

### C2. Evidence identity, storage and publication (AC2)

Use one trusted feature resolver and one local evidence contract for tracked,
ignored or untracked records, inside or above application repositories. The
parent may have no Git. Do not infer authority from a path supplied by a caller.

A frozen input manifest must bind, at minimum:

- Current contract and gate/criteria identity; feature/run and repository scope.
- Source base/head and review range for each included repository.
- Approved requirement raw-byte hashes/lengths and authority references.
- Typed consumed-evidence references, retained bytes and original provenance.
- Check command/configuration, relevant dependency/environment assumptions,
  and evaluator/execution qualification needed for applicability.

A result binds its manifest, original evaluated candidate/scope, gate verdict(s),
coverage limits and actual receipt. Result publication is separate from frozen
inputs. Timestamps and paths are provenance, not sufficient content identity.
The core checks these bindings at preparation, result admission and milestone
passage; hashing only the reviewer prompt is insufficient.

Capture regular files within trusted roots, reject traversal and symlink/path
substitution, preserve exact bytes and publish verified complete bundles
exclusively. Repeating an identical operation can reconcile; conflicting bytes
under an existing identity must fail without overwrite. Failed operations do
not append passage. Orphans/partial writes are not PASS, and missing evidence
cannot be concealed by an old successful event. Do not invent an atomic
transaction across the filesystem and journal.

The isolated reviewer receives only permitted source/requirements/review packet,
with read-only access and current network restrictions. Retained history must
not leak through tracked source or diffs. Multi-repository reviews expose only
the explicitly declared participating scope, not arbitrary sibling files.

Application clean/source/PR checks remain. Evidence inventory derives from
validated manifests and recorded references; no evidence commit/push or caller
changed-path list substitutes for proof. Source changes during execution retain
a historical result but prevent current acceptance until applicability is proven.

Retain referenced inputs and outputs including failures. Do not automatically
prune, create Git repositories/remotes, edit ignore policy or claim backup.
Workspace deletion requires an applicable keep/archive/discard decision;
archival is claimed only after copy verification outside the deletion scope.

### C3. Evaluator independence and reviewer knowledge (AC3, AC5)

A qualifying fresh evaluator has not inherited the implementer's conversation
or acted as implementer for the assessed change. Requesting model assessment
through the execution service records the role and source-bound input packet;
self-asserted independence or an implementer-authored verdict is insufficient.
A grouped code/spec execution must return both separately validated verdicts;
a missing or invalid one leaves its own gate unsatisfied.

Supply requirements, prior reviewer results and scope/limitations, relevant
open/affected findings, current diff, claimed resolutions and supporting proof.
Label claims separately from reviewer conclusions. Preserve original reports
and stable finding/class identities. Verify open findings and claimed fixes;
recheck affected closures and carry unaffected closures only through justified
applicability. The reviewer searches changes/interactions for new defects.

A newly discovered instance of a resolved class remains reportable. Reopening
requires current evidence. Blocking findings must cite the violated approved
criterion or applicable gate rule and current source/evidence. Advice,
unsupported concerns and unrelated pre-existing defects are distinguishable
follow-ups, not automatic scope expansion. Prior verdicts are not authority.

### C4. Applicability and delta assessments (AC4)

Keep execution identity distinct from current applicability. Exact equivalent
required inputs plus intact evidence and qualifying policy permit reuse;
a new SHA with identical relevant content, an attempt ID, timestamp or unrelated
report alone does not invalidate proof. Actual relevant changes do.

Use conservative declared scope and available project/build manifests. Changes
to a shared helper, dependencies/lockfile, runner/configuration, migration or
requirement cannot be classified as unrelated merely from filenames. Where
relevance is unknown, obtain wider fresh evidence. External observations carry
their explicit state/validity conditions; no blanket age threshold is introduced.

A delta record names earlier review proof, the old/new candidate and change
range, changed scope and interactions examined, affected finding dispositions,
new findings, remaining limits and current verdict. Its evaluator must qualify
for each supplemented gate. The core verifies references and coverage claims
are present/consistent; semantic coverage is the independent evaluator's
responsibility. Unsupported model reassurance cannot extend evidence.

A final milestone admits the union of applicable earlier proof and qualifying
refreshes only if every required obligation is covered. Old FAIL/unavailable
results remain in history; a new result or scoped waiver changes current
eligibility, never the historical result. Missing bytes require exact restoration
and revalidation or fresh evidence, not silent reconstruction from current files.

### C5. Human decisions and current resume entry (AC6, AC8)

A human-decision record contains decision kind, affected gates/findings or
old/new commitments, candidate/risk scope, known consequences, authorized actions,
actual instruction/quote and available conversation/message provenance. A clear
response to a specific proposal suffices. Host metadata is optional when absent;
never fabricate it. Actor labels remain cooperative rather than authentication.

Record/apply/validate is one semantic operation from the user's perspective,
with repeat-safe internal steps and visible incomplete status after interruption.
No repeated approval is needed for the same decision. Amendments retain old/new
versions and refresh affected proof. A non-waivable gate requires an explicit
applicable policy amendment. Factual truth and actual authority cannot be waived.

Exceptions default to the specified risk/candidate; relevant changes recheck
applicability and require renewed authority if outside scope. Bookkeeping does
not. Standing exceptions need explicit scope. Merge/deploy authority must be
expressly included. Display accepted exceptions independently of check verdicts;
observe actual integration separately, including externally performed merges.

For old work, the current-protocol resume operation uses preserved documents
and observed instructions to establish a new current run under the same logical
feature identity. Keep old runtime files intact in their historical location or
an explicitly identified retained location; never overwrite/interpret the old
journal as new passage. An active-run reference changes only after the new
run is durably established. No historical model interpreter or automatic event
converter is required. The operation reports unsupported old state and exact
missing current obligations rather than becoming unusable on an old lock.

Resumption alone does not approve changed requirements or new merge actions.
Where unchanged commitments and applicable authority can be substantiated,
retain them without another interview. If authority is missing or ambiguous,
ask only for the missing concrete decision. Current admission validates reused
artifacts against current contracts; unsupported proof is refreshed. Interrupted
resume leaves a recoverable identifiable run, not two competing authorities.
The same current-run entry applies to this GateReeve feature after cutover.

### C6. Surfaces, hooks and real-project use (AC7, AC8)

Expose a compact current view of phase/authorized scope, required obligations,
applicable evidence and coverage, stale/missing inputs, exceptions, actionable
next operations and enforcement coverage. CLI, native skills and desktop use
the same core view. Remove incidental ordering controls and legacy execution
choices; do not preserve the graph merely for a desktop dependency diagram.

High-level operations own IDs, structured requests, receipts and routine
record generation. A readiness declaration does not launch a model evaluator;
an explicit execution request does. Exact duplicate recoverable requests
reconcile prior work instead of launching duplicate costly jobs. Errors retain
a useful cause and remedy without exposing secrets or raw provider context.

Protected action adapters deny when the core check fails or is unavailable,
recheck source/action immediately before execution, and record actual outcomes.
Hooks, where a supported host can intercept the action, invoke these same
checks. Report per host/action whether protection was exercised, is adapter-only,
or is cooperative. Current SessionStart injection alone is never called hard
enforcement. Unsupported host interception is reported, not guessed or advertised.
Do not block ordinary conversation, corrective edits or individual commits.

Use one current set of schemas, operations, skills and distributed adapters.
Unsupported old versions get actionable resume guidance, not legacy replay or
silent conversion. Local build/runtime smoke must exercise current consumers.
No public release, production credentials or deployment is required to prove
this feature before merge. Actual publication/installation retains its own gates.

Existing evidence/receipts make repeated checks, available token/cost/time data,
human interruptions, supported findings and later defects/rework inspectable.
Missing metrics are unknown, not zero; summed provider time is not wall time.
Real-project experience drives iteration without a fixed performance threshold,
mandatory comparative benchmark, extra audit gate or dashboard subsystem.

## Scope and verification boundaries

Source/core/helper/schema, CLI/native plugin and necessary desktop consumer
changes are in scope. Local build and integration checks establish pre-merge
behavior. Host capability probes must distinguish a mocked adapter assertion
from actual interception. If no action hook exists for a host, test its protected
adapter and explicitly expose the limitation; do not claim the host can block
arbitrary commands. Any stronger enforcement requirement would need a design
amendment rather than a fictional passing test.

Real-project observation after use is feedback, not an additional pre-merge
passage requirement. Public release, remote installation, external branch
protection setup, application changes and production deployment are outside
this implementation's implied authority. No backward compatibility or automatic
migration test suite is required; preserve safety outcomes still relevant under
the current contract rather than obsolete orchestration assertions.

- **2026-10-24 (D11, authorized by Trent):** Add R22/R23 under existing AC6/AC7.

  records exact candidate/action with grant provenance, and rechecks grant

  still requires actual integration and complete-feature/finalization proof.
  Existing exact candidate decisions/exception policy remain supported.
  Open drafts are the default; explicit closed drafts remain supported.
