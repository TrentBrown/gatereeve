Background

The beginner's model: Electron has two unequal worlds

An Electron application looks like a web page, but its trusted operating-system work belongs in the main process. The renderer paints buttons and terminal cells. It should not receive a general “run this executable” capability, because a renderer compromise would then become arbitrary process execution.

Main launches the PTY in the saved worktree, returns an opaque session ID, and streams bounded output. The renderer may write keystrokes, resize, terminate, or restart that exact project-owned session. It cannot choose the shell, cwd, environment, PID, or another project's session.

The existing GateReeve contract

GateReeve Desktop was already a hardened observer of governed workflow state: sandboxed renderer, context-isolated preload, custom protocols, strict content security policy, and main-owned filesystem authority. This change extends that architecture instead of punching through it.

Intuition

The core idea is “capability without orchestration.” Imagine two saved projects, alpha and beta. Revealing alpha lazily creates one shell in /work/alpha. Hiding it does not kill it. Selecting beta creates nothing until beta's terminal is explicitly revealed. Returning to alpha shows the same foreground process and scrollback.

Trusted routing

The renderer never says “spawn in alpha.” Main resolves whichever ready saved project is selected.

The asynchronous edge case is subtle. Xterm is loaded only when needed. If the user switches projects while that module loads, the original request must be abandoned rather than attached to the new project. The implementation rechecks project identity and explicit visibility after every asynchronous boundary.

const project = selectedProject();
const { Terminal, FitAddon } = await loadTerminalLibrary();

Code walkthrough

1. Trusted PTY manager

terminal-manager.js owns the per-project registry, account login-shell resolution, bounded output, lifecycle state, opaque IDs, and restart behavior.

2. Narrow bridge

Shared contracts, preload, and IPC independently reject extra fields, bad dimensions, oversized input, stale IDs, cross-project access, and wrong lifecycle states.

3. Bottom-panel UI

The center layout control and Command/Ctrl+J toggle a resizable bottom panel. One xterm view is retained per project for the application lifetime.

4. Destructive guards

Removing a project or quitting with live terminals offers exactly Cancel or Terminate-and-continue. Cleanup targets the PTY group and captured descendants.

5. Native packaging

Only exact xterm assets are protocol-served. Node-pty prebuilds and executable helpers are unpacked from ASAR and verified for both macOS architectures.

6. Regression depth

Fake PTYs cover exhaustive state; real PTYs prove OS behavior; packaged native jobs launch the exact universal DMG on Apple Silicon and Intel.

Data events and the initial snapshot

A PTY can emit output before the asynchronous ensure call returns its snapshot. Blindly writing both duplicates startup text; blindly discarding events can lose later text. The renderer removes only the exact suffix/prefix overlap, then appends the remainder.

snapshot output:  "ready\r\n"
early events:     "ready\r\nnext"
overlap:          "ready\r\n"
rendered result:  "ready\r\nnext"

Delivery without a signing catch-22

The final change in this PR clarifies a process invariant exposed by the terminal's native dependency. Protected Apple credentials intentionally accept only reviewed main commits. Therefore a topic-branch PR cannot honestly produce the final Developer ID/notarized artifact.

After merge

Release acceptance

  • Developer ID signing
  • Notarization and stapling

The terminal spec keeps both requirements. It merely assigns each to the first boundary where its evidence can exist. The canonical spec-draft and spec-validate guidance now prevents future features from recreating the same impossible pre-merge gate.
