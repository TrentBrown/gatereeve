Background

A pull request boundary is a governed sequence of checks. GateReeve records each result against the selected source and its dependency events. Full Verification and an independent Judge establish formal evidence, then the packet and exact-head human review control the next step.

When defects are discovered only at that boundary, the implementer has to repair code and prepare another complete attempt. This slice adds an earlier discovery checkpoint after fast checks and focused tests. Earlier slices supplied compact independent inputs and the guarded post-merge completion recovery path.

This slice changes the route into formal review. The formal gate graph, its freshness requirements and human merge authority remain intact.

Intuition

Implementer

Finish the slice, run focused checks and explicitly declare readiness.

Advisory

Inspect the pinned full scope in a fresh read-only context. Full Verification is pending.

Formal boundary

Perform complete current Verification and independent Judge review.

For example, a late response might overwrite a newer choice. A failure should lead to analysis of every writer and the violated invariant, with regression coverage, before the next readiness declaration. The rerun checks earlier findings and continues looking across the entire slice.

The formal Judge has no advisory history, earlier review reports, raw decision journals or bypass reasons. It assesses the resulting code against approved requirements and current formal Verification.

Clean

READY_FOR_FORMAL_REVIEW, without formal certification.

Findings

Fix the defect class and declare the revised slice ready, or retain a source-bound reason.

Unavailable/pending

A recorded reason may admit formal entry. It never waives a formal requirement.

A deterministic input comparison permits a clean advisory to survive evidence-only commits. Changes to source, tests, build/configuration, dependencies, approved requirements, declared evidence or review capability/resources invalidate it.

Check your understanding

1. A clean advisory review establishes what?

Advisory discovery is noncertifying. Mandatory formal checks and exact-head human approval still govern delivery.

2. Which change can preserve a clean advisory result?

The helper compares complete reviewed input bindings, including code, requirements, test evidence, resources and capability policy.

3. What does the formal Judge receive?

Advisory reruns get a fix checklist. The formal Judge independently evaluates the resulting code with history excluded from inputs, diff and repository.

4. How is an existing formal FAIL without a separate concern list handled?

The adapter preserves valid historical formal contracts while requiring class analysis and regressions before a revised declaration.

5. The advisory is unavailable. What may a retained reason do?

A source-bound reason is permission to proceed through formal review, never a PASS or waiver.
