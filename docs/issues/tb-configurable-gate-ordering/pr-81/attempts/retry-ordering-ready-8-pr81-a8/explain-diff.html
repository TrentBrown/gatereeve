Background

Start with the workflow basics

A workflow boundary is the point where an implemented slice becomes a reviewable change. Verification, spec assessment and independent reviews produce evidence. The protocol records those results against exact inputs; human acceptance and merge are separate actions.

A gate is ready when its required predecessors have acceptable, current results. If a predecessor is reviewed again, its new event has a different identity. Evidence that depended on the previous event becomes stale even if the report text is identical.

GateReeve already has a dependency graph. Module manifests declare hard prerequisites through dependsOn and conditional completion ordering through after. The old diagram grouped checks by depth and used broad connectors, which could imply relationships the graph did not contain.

Three edge meanings

A required prerequisite must be enabled. A module ordering edge applies while its predecessor is enabled. An owner ordering edge applies while both selected endpoints are enabled. All three affect eligibility and predecessor-event freshness. A visual row merely reflects dependency depth.

The new repository policy stores owner edges separately, preserving module definitions and their digests. Existing schema-1 policies and pinned history retain their interpretation.

Intuition: a small edge, a precise consequence

Choose Judge after Code Review. Verification remains Judge’s hard prerequisite. The added edge makes Judge wait for Code Review and binds the exact Code Review event. It does not give Judge that review’s findings.
