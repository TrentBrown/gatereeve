From a flat overview to a progressive workflow hierarchy

This slice turns the workflow overview into an observational navigator. A user can select a feature state, then a delivery slice, then a boundary attempt, then a gate—while the actual workflow state remains a separate, clearly labeled fact.

1 · Background

Two kinds of state occupy the same screen

GateReeve reads a governed feature record and projects it into a Desktop snapshot. That snapshot contains the workflow’s authoritative current state, its delivery slices and boundary attempts, a graph of gates, and an inventory of readable artifacts. The renderer is an observer: it may choose what to inspect, but it must not imply that inspection changes workflow authority.

Workflow state

Authoritative and protocol-owned. For example, the feature can currently be DELIVERING_SLICES, and one slice can be active.

Current / Active

Inspection selection

Ephemeral and renderer-owned. A user may inspect DESIGNING or a historical slice without changing the feature record.

Selected
Key definition. “Current” and “Active” describe the workflow projection. “Selected” describes the user’s viewing context. A single item may carry both labels, but the meanings never collapse into one.

Before this PR

The overview rendered states, slices, attempts, and gates in a mostly linear presentation. State nodes were not observational controls. The boundary area could show attempts unrelated to the slice a reader had in mind, and selecting a gate updated a summary area rather than consistently opening the corresponding inspector tab.

The inspector contract already existed

The preceding application-shell slice established a unified right-hand inspector with closeable tabs. This PR reuses that contract. Named artifacts such as design.md and boundary.json use canonical artifact identities; gates without files use an honest virtual “Gate Detail” tab rather than inventing a filesystem artifact.

2 · Intuition

3 · Code

The change in four layers

A. Presentation helpers make selection deterministic

presentation.js now supplies small, pure lookup functions. They map feature states to named artifacts, choose a valid slice or attempt with sensible fallbacks, and locate boundary or gate evidence within the snapshot inventory.

selected slice = requested slice
              ?? active slice
              ?? most recent slice

selected attempt = requested attempt in selected slice
                ?? active attempt in selected slice
                ?? most recent attempt in selected slice

This keeps fallback rules testable and prevents the renderer from showing an attempt merely because it happens to be globally newest.

B. Workspace state remembers the observational path

The existing per-project, in-memory workspace now includes selectedGateId alongside selected feature state, slice, and attempt. The data stays renderer-owned and session-scoped. No workflow transition, new IPC authority, or relaunch persistence is introduced.

workspace-state.js — adds selectedGateId
presentation.js — resolves state, slice, attempt, and evidence

C. The renderer turns the hierarchy into accessible controls

renderer.js changes state nodes, slices, and gates into native buttons with aria-pressed. Text labels expose Current, Active, and Selected semantics, so neither meaning depends on color alone.

Disclosure is driven only by the selected feature state:

DESIGNING / SPECIFYING / PLANNING / COMPLETE
  → open the mapped named artifact

DELIVERING_SLICES
  → reveal slices and the selected slice's boundary

FINALIZING
  → reveal closeout status and conditions

The closeout surface deliberately distinguishes Blocked, In progress, and Ready. This is the remediation that followed the first review attempt: an active slice can no longer coexist with a misleading “Ready” label.

D. Artifact reads obey selection identity

A subtle race lived at the junction of hierarchy navigation and inspector loading. File fingerprints indicate freshness, but they do not identify which artifact the user selected. Two artifacts can have equal or unavailable metadata. Therefore openArtifact() advances the request generation and clears the in-flight fingerprint before rendering the new active tab.

async function openArtifact(artifact) {
  artifactReadSequence += 1;       // older completion is now stale
  workspaceStore.openArtifact(...);
  selectedArtifactFingerprint = null;
  artifactInFlightFingerprint = null;
  renderInspector(...);
}
Why this matters. Without generation invalidation, a rapid switch from an artifactless gate to an HTML-backed gate could open the right tab yet leave it unloaded because an older read shared the same weak freshness fingerprint.

Tests and fixture

The fixture now supplies enough governed data to display an active boundary, parallel gate markers, canonical evidence, and completion content. Unit and renderer tests cover independent selection semantics, scoping, empty states, natural markers, inspector identities, race invalidation, accessibility, and closeout status.

presentation.test.js — pure fallback and artifact resolution
renderer.test.js — disclosures, semantics, closeout, inspector race
workspace-state.test.js — per-project selected gate state
accessibility.test.js — pressed-button and reduced-motion contracts
visual-fixture.js — deterministic production-module rendering
