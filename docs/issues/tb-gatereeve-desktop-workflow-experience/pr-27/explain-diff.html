GateReeve Desktop · PR #27 · P1-P3

Trust the project before building the workspace

This slice establishes the contracts beneath the coming IDE-like interface: which directories count as projects, how saved projects survive relaunches, how observation moves between them, and how slices and gates receive stable order markers.

Background

The observer before this change

GateReeve Desktop already read one governed feature record through a narrow main-process adapter. The renderer could inspect snapshots, artifacts, attempts, history, model data, and session context. But the application treated directories as a short “recent worktree” list. It lacked a durable project identity, strict admission results, and lifecycle operations suitable for a project sidebar.

Electron divides this responsibility deliberately. The renderer is untrusted presentation code. The main process owns filesystem access, path canonicalization, preference writes, protocol reads, watchers, and GitHub polling. The preload exposes only validated named operations. PR #27 preserves that boundary.

User choiceOne explicit directory
Main processCanonicalize and inspect
ProtocolClassify governed or diagnostic-only
RendererReceive validated project summaries
Governed is an admission rule, not a repair action. Missing, legacy, inconsistent, incompatible, and unreadable records produce diagnostics. GateReeve does not adopt, rewrite, or initialize them.

Why protocol order belongs below the UI

The new visual hierarchy will number slices and gate stages. Those markers must describe durable workflow meaning rather than the renderer's current sort order. Therefore slice ordinals and dependency-stage labels are projected by the canonical protocol core and only rendered later.

Intuition

A project is a trusted reference

Imagine choosing /work/reef. The main process resolves symlinks, verifies that the result is a directory, resolves its feature record, and reads a snapshot. Only a supported governed snapshot becomes a normal project. The preference file stores the canonical path—not the snapshot, GitHub data, artifacts, or project content.

selected path  /work/reef-link
real path      /work/reef
snapshot mode  governed
saved value    /work/reef
watcher        active project only

If that project becomes incompatible next week, it stays in the saved list as Needs attention. That is different from adding a new invalid directory: a new invalid candidate is never admitted.

Order is semantic, not cosmetic

Slices receive 1, 2, 3… when proposed. Gates receive the longest dependency depth. Gates at the same depth receive alphabetic branches in pinned model order:

1→2→3→ 4a4b4c4d→ 5→6→7

Code walkthrough

1. Canonical protocol projection

projection.js now assigns each proposed slice a stable delivery ordinal. Its dependency walk detects cycles and unknown dependencies, computes stages, and labels parallel peers. snapshot.js validates these fields and adds completion-report.md to the trusted artifact inventory. Canonical source is restaged into the Desktop resource bundle, and parity tests prevent drift.

2. Preference schema v2

preferences.js replaces capped recents with projectPaths and lastProjectPath. Schema v1 values migrate deterministically. Add never reorders an existing reference; activate changes only the last pointer; reorder requires the exact saved set; removal selects the nearest surviving reference.

3. Strict admission

project-registry.js turns one selected directory into either a Ready summary or a structured diagnostic containing the selected path, resolved feature home when known, failed checks, and pinned/supported model versions. It performs no writes.

4. Coordinator lifecycle

At startup the coordinator validates every saved project once, restores the exact last active path, and creates observation infrastructure only for that active project. Switching increments a generation token, stops old polling and watchers, publishes local state, then enriches Git and GitHub independently. Removal edits preferences only and activates the nearest saved project.

Review remediation: the first pinned attempt found that returning inside try captured refreshing: true before finally cleared it. The remediated head returns only after cleanup; direct IPC results and subscriber publications now agree.

5. Narrow Electron contract

The IPC/preload surface now names four project-reference operations: add, activate, reorder, and remove. Every request is bounded, the exact top-level application frame remains authenticated, and filesystem/artifact reads are still named rather than arbitrary.
